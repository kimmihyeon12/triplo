## Context
이 프로젝트는 국내 여행 추천, 선택형 일정 구성, 실제 방문 사진 지도를 연결하는 신규 반응형 웹/PWA 기획이다. 초기 사용자는 본인과 친구들로 확정했으며 비용 최소화와 향후 확장을 고려한다. 참조 Notion은 열리지 않아 원본 시각 디자인을 확인하지 못했다.

## Goals / Non-Goals
목표: 서울 중심 AI 일정 검증, 전국 장소 저장과 기록, 수동 편집 가능성, 작은 캐릭터의 성장.
제외: 자체 내비게이션, 무단 정보 수집, 전체 국가 3D 지도, 실시간 공동 편집, 예약 결제, 상시 GPS.
이 문서는 설계 초안이며 앱 구현을 시작하지 않는다.

## Decisions
- 적용 시점: 현재 진행 중인 작업을 먼저 완료한다. 사용자가 이후 별도로 리팩터링을 지시하면 최신 코드를 확인하고 ARCHITECTURE.md와 tasks 9절을 적용한다. 설계 문서가 존재한다는 이유로 현재 작업 중 업그레이드·구조 변경을 시작하지 않는다.
- 아키텍처·상태관리 기준은 `ARCHITECTURE.md`다(2026-09-09). 최신 사용자 결정에 따라 Angular 21 + NgRx Signals 21.x로 업그레이드하고 현재 `app/`는 유지한다. 참고 프로젝트의 기능별 feature/ui/data/model/util, UI 입력·출력, 서비스 private `signalState`를 채택한다. Zoneless는 버전 업그레이드와 분리 검증하며 기본 폼은 typed Reactive Forms, 조회는 Promise/HttpClient·RxJS다. 21의 experimental API인 Signal Forms·rxResource는 필요 시 제한된 흐름에서 실증한다. 여행 목록·작업 화면·AI·경비·동행 상태의 수명을 분리하고 여행별 실패 입력 보관소와 최신 응답/저장 버전 검증을 둔다. 현재 Angular 20 설치 상태와 목표 구현을 구분한다.
- 최신 사용자 우선순위는 기존 수동 알파 → 지도·장소·경로 실제 연결 → 선택형 AI 실제 연동·화면 검증 → Supabase 연결이다(기획안 26절). 지도 렌더링·검색·경로·AI는 별도 어댑터와 검증 항목을 둔다. AI·비공개 API 호출은 로컬 개발용 서버에서 처리하고 서버 비밀키를 Angular 번들에 포함하지 않는다. Supabase 미생성을 지도·AI 작업의 차단 조건으로 두지 않고 친구들의 실제 사용 전 서버 저장·RLS와 API 호출 접근 제한을 검증한다.
- 프레임워크는 Angular(standalone 컴포넌트, signals) + TypeScript다. 내부 알파는 Angular 20으로 작성했고 최신 사용자 선택에 따라 Angular 21로 올린다. 클라이언트 중심 PWA와 `app/` 위치는 유지한다. 코드 업그레이드와 빌드·테스트 검증은 tasks 9절의 별도 미완료 작업이다.
- 내부 알파 저장 계층은 `TripRepository` 인터페이스 뒤의 localStorage 구현이다. 화면은 상태 서비스와 계약을 통해 접근한다. Supabase 연결 시 어댑터 분리는 유지하되 AI 적용·일정 변경·초대·정산에 필요한 용도별 명령, 버전 검사와 중복 방지를 설계하며 현재 전체 여행 CRUD 계약을 영구 고정하지 않는다. 도메인 규칙(날짜·숙박·요약·기간 변경)은 프레임워크 독립 모듈로 두고 Vitest로 검증한다. 화면별 입력·빈 상태·오류·저장 결과는 `docs/알파-화면설계-v0.1.md`가 원본이다.
- 제품 화면 디자인은 Impeccable 절차로 결정했다. PRODUCT.md·DESIGN.md·`.impeccable/surfaces/` 방향 계약이 시각 결정의 원본이다.
- Supabase PostgreSQL을 DB로 확정한다. 무료 플랜부터 시작하고 Supabase Auth 및 비공개 Storage를 연계하는 방향으로 설계한다. 사용자 소유권·RLS·마이그레이션을 적용하고 사진 파일은 DB와 분리한다. PostGIS는 필요한 공간 질의에 맞춰 적용한다. 실제 계정·프로젝트 연결과 유료 전환은 별도 상태로 관리한다.
- 장소·경로·AI 제공자를 어댑터로 분리한다. 장소의 provider/id와 좌표를 보존하고 제공자 간 표시·캐시 약관을 먼저 검증한다.
- 지도 표시와 장소 검색 제공자는 카카오맵 JavaScript SDK로 확정했다(2026-09-09, 기획안 26절). 앱은 `MapProvider`·`PlaceSearchProvider` 인터페이스만 사용하고, 런타임은 카카오 구현, Playwright 테스트 앱은 외부 호출 없는 픽스처 구현을 주입한다. 브라우저 공개용 JavaScript 키는 `app/public/app-config.json`(커밋 금지, 예시 파일 제공)에서 읽고 카카오 콘솔의 등록 도메인으로 제한한다. 키가 없으면 지도·검색은 ‘연결 안 됨’ 상태를 표시하고 나머지 기능은 동작한다.
- 좌표는 사용자가 검색 결과를 고른 경우에만 `location`·`placeRef`(provider/id/url)로 저장하고 `locationStatus`를 verified로 둔다. 직접 입력·위치 지우기는 unverified다. 지도에는 확인된 좌표만 순번 마커로 그리고, 순번을 잇는 점선은 ‘방문 순서 안내선’이며 경로가 아니다.
- AI 추천은 로컬 LLM을 로컬 개발 서버가 호출하는 구조로 간다(2026-09-09 사용자 결정). 유료 API 계약은 하지 않는다.
- AI 일정 만들기는 지역→날짜·기간→동행→취향→이동수단·일정 밀도의 선택형 단계로 받으며 자유 텍스트는 보조다. 트리플 공개 웹에서 실제 확인한 마지막 질문은 일정 밀도이고, 복수 지역·실제 날짜·이동수단은 우리 앱에 맞춘 확장이다. 입력·시각·결과 선택 규칙은 `docs/트리플-맞춤일정-분석.md`와 기획안 25절을 따른다.
- AI는 장소 후보와 설명을 만들고 실제 장소 조회 결과로 검증한다. 영업 여부나 예약 가능 여부를 생성으로 대체하지 않는다.
- 추천 결과의 검증된 방문 항목은 모든 날짜에 걸쳐 기본 선택한다. 선택은 저장과 분리하며 명시적 담기로만 선택한 항목을 여행에 추가한다. 결과 ID와 방문 항목 ID로 선택 상태를 관리해 같은 장소의 다른 날짜 방문을 구분한다. SavedPlace와 TripStop을 분리한다.
- 경로 개선은 고정 순서, 출발·도착점, 체류 시간을 고려한다. 전역 최적해를 보장한다고 표현하지 않는다. 실제 시간 공급자 후보는 TMAP이며 라이브 검증이 선행한다.
- Expense는 Trip에 속하고 TripStop·AccommodationStay에 선택적으로 연결한다. 연결 대상 삭제 시 지출은 연결 해제로 보존한다. 예산·정산 계산은 원화 정수 연산으로 하고 결제·송금 연동은 하지 않는다(기획안 24절).
- 공유·정산은 Supabase 연결 이후 친구 사용 단계에 구현한다(기획안 27절). 소유자 장부 관리와 승인된 동행의 읽기부터 제공하고 공동 일정 편집은 후속이다. AI·메시지·결제 API 없이 링크 복사와 정수 계산을 사용한다.
- TripParticipant는 회계상 사람 ID, TripMember는 로그인 계정의 접근 권한이다. 미가입·동명이인·탈퇴가 과거 분담액을 바꾸지 않도록 분리하고 계정 연결은 소유자가 확인한다. TripInvite는 type=link/code로 구분한다. 링크는 일회용, 8자리 코드는 여러 계정이 요청 가능하며 모두 기본 7일 만료·해제·소유자 승인을 요구한다. 코드는 혼동 문자를 제외한 암호학적 난수로 생성하고 정규화한 값의 서버 비밀값 기반 HMAC을 저장한다. 활성 코드 고유성과 여행당 한 코드 제약을 두고 충돌 시 다시 생성한다.
- TripJoinRequest는 여행·계정별 요청 상태와 invite_id를 가진다. 요청·승인 시 초대 유효성과 멤버 상태를 원자적으로 확인한다. 코드 재발급·만료는 대기 요청을 만료시키되 이미 승인된 멤버는 유지한다. 같은 계정의 재시도는 멤버·요청을 중복 생성하지 않는다. 잘못된 코드의 존재 여부·여행 정보를 노출하지 않고 계정·접속 출처별 시도 제한을 적용한다. 비로그인 입력은 로그인 후 이어가며 코드 원문은 분석 로그에 기록하지 않는다.
- 상단 요약(기획안 28절)은 Asia/Seoul 달력 날짜 기반 D-day·기간·지역 순서와 권한별 지출 합계·승인된 동행 프로필을 분리한다. 예정일 경과는 여행 완료로 취급하지 않는다. 지출 미연결은 0원으로 표시하지 않고 프로필 미연결은 기본 아이콘·준비 중으로 표시한다. 대기 프로필은 소유자 승인 목록에서만 노출한다. AA.png 확인 전 시각 배치를 확정하지 않는다.
- TripShare는 선택한 날짜·장소와 명시적으로 포함한 숙소 이름·위치만 가진 읽기 전용 스냅샷이다. 기본 7일 만료, 해제·재발급·미리보기 후 갱신을 지원한다. 토큰은 암호학적 난수로 생성하고 서버에는 해시를 저장한다. 요청마다 만료·해제를 검사하고 공유 응답은 no-store로 전달한다. 이미 복사한 데이터 회수는 보장하지 않는다.
- 승인된 동행은 최신 허용 일정과 공동 경비만 읽는다. 사진·개인 메모·예약번호·개인 경비는 별도 소유자 전용 데이터로 유지하며 RLS와 필드 허용 목록을 적용한 응답 경계를 둔다. 링크는 원본 테이블 읽기 권한을 주지 않는다.
- Expense는 개인/공동 범위와 결제자 1명을 가지며 ExpenseShare에 선택한 사람별 원화 부담액·배분 순서를 저장한다. 원금은 양수, 분담은 0 이상·합계 일치를 검증한다. 균등 분배의 나머지는 저장된 참여자 순서로 1원씩 배분하고 멤버 변경 시 자동 재분배하지 않는다.
- SettlementTransfer는 보낸/받은 사람·금액·날짜·기록자·취소 이유를 가진 수동 수령 기록이다. 잔액은 결제−부담+보낸 수령확인액−받은 수령확인액으로 계산한다. 양수 채권자·음수 채무자를 안정된 ID 순서로 대응해 송금안을 만들며 최소 횟수는 보장하지 않는다. 수령액은 양쪽 미정산 잔액 이내로 제한하고 원 지출 총액에 더하지 않는다. 지출 변경 후 수령 기록을 보존해 반환액을 포함한 차액을 다시 계산한다.
- 공동 장부 쓰기는 소유자만 가능하며 장부 버전·요청 고유 키·트랜잭션으로 오래된 수정과 중복 수령을 막는다. 취소는 원본을 지우지 않고 이력을 남긴다. 실시간 구독 없이 진입·새로고침·저장 후 조회하고 실패 입력은 보존한다.
- Visit와 Photo는 TripStop 삭제와 분리하여 기록을 보존한다. XPEvent에 이벤트 고유성을 적용한다.
- 지도는 실용적인 2D를 기본으로 하고 3D는 캐릭터 홈과 완료 연출에 한정한다. 경량 정적 대체 화면을 제공한다.
- 기본 데이터는 비공개로 저장한다. 위치 권한 거부 시 지역 선택을 제공하며 사진 위치 메타데이터를 제거한다.
- 초기 AI 품질은 서울, 하루 최대 8장소 제안으로 검증한다. 여행은 시작일·종료일 기반으로 여러 박을 지원하며 1~3일로 제한하지 않는다. 전국 저장·기록은 별도로 지원한다.

## Risks / Trade-offs
- 공식 검색 API에 상세 영업정보와 평점이 충분하지 않음 → 미확인 표시, 원문 확인, TourAPI 보완. 수집 가능성을 출시 전 보장하지 않는다.
- 경로 API 비용·도보 지원·제공자 결합 조건 불확실 → 20개 서울 장소 및 대표 경로로 PoC 후 공급자를 확정한다.
- 지도앱 링크가 OS/브라우저별로 다름 → 실기기 설치/미설치 조합과 좌표 방향을 검증한다.
- 3D 모바일 성능 비용 → 핵심 지도 화면과 분리하고 정적 대체 제공.
- 초기 기능 범위가 큼 → 내부 알파는 선택·수동 일정, 외부 베타는 사진 지도·성장까지 순차 검증한다.

## Open Questions
확정 서비스명과 캐릭터, 월 운영 예산, 일반 공개 시점, 디자인 참조 원본. 초기 대상은 본인과 친구들, DB는 Supabase로 확정되었다.

- 캐릭터 방향: 콩·씨앗·새싹 콘셉트는 제외한다. 여행 경험치와 레벨에 따라 성장하는 독립적인 3D 동행 캐릭터를 사용한다. 구체적인 외형과 서비스명은 미정이다.

## Multi-night stays
AccommodationStay는 Trip에 속하며 숙소명, 선택적 PlaceRef/주소/좌표, 체크인·체크아웃 날짜, 선택적 시각, 사용자 입력 예약 상태와 메모를 보관한다. 숙박 날짜 구간은 체크인 포함·체크아웃 제외로 계산한다.
연박·숙소 변경·미정 숙박을 지원한다. 숙박 중복과 여행 기간 밖 예약은 확인 대상으로 표시한다. 당일 및 여러 박 여행의 날짜를 모두 생성한다.
숙소 기반 일별 출발·종료 지점은 제안으로 제공하고 사용자 지정값을 보존한다. 위치 미확인 숙소의 이동시간은 생성하지 않는다. 확정한 숙소와 시각 제약을 경로 정리에 반영한다.
여행 기간 변경 시 영향받는 항목은 재배치 대상으로 보존하고 변경 확인을 받는다. 숙소 출발·복귀와 보상 가능한 방문 이벤트를 구분한다.

## Multi-region trips
Trip은 순서가 있는 복수 지역을 가질 수 있고 TripDay는 하나의 지역에 종속되지 않는다. 지역은 일정 정리를 위한 정보이며 지역 변경이 숙소 변경을 강제하지 않는다. 같은 날짜의 서로 다른 지역 방문지와 숙박을 하나의 시간순 일정으로 표현한다.
지역 간 이동은 앞뒤 실제 TripStop 또는 숙소 위치 사이의 이동 구간으로 다루며 별도 이동시간을 중복 가산하지 않는다. 조회값은 출처·조회 시점과 함께 관리하고 미조회값은 확인 필요로 둔다. 사용자 확정 지역 순서·예약·숙소 시각을 보존한 변경안만 적용 전 비교한다.
초기 하루별 차량/도보 경로 비교를 유지한다. 기차·시외버스 등 미지원 구간의 이동수단·출발·도착 시각은 사용자 입력과 미정 상태로 관리하고 자동 시간표 조회·혼합 이동 최적화와 구분한다. 미정 이동이 있으면 일정 실현 가능성을 확정하지 않는다. 복수 지역 수동 편집과 서울 밖 AI 품질 검증을 구분한다.
지역 순서·이동일 변경은 영향받는 일정·숙소·예약을 확인한 뒤 반영하며 지역 삭제로 기존 일정·방문 기록·사진을 연쇄 삭제하지 않는다.

## AI accommodation drafts
선택한 Trip을 문맥으로 자연어에서 숙소명·지역·숙박 구간을 추출하고 실제 숙소 검색 결과와 연결한 등록 초안을 만든다. 초안은 AccommodationStay와 분리하며, 사용자 후보 선택·날짜 수정 후 명시적 적용 시에만 숙박과 날짜별 연결을 저장한다. 상대 날짜는 여행 기간을 기준으로 실제 날짜로 표시하고 불명확한 날짜·동명 숙소는 사용자 확인으로 해소한다. 검색 실패 시 직접 입력을 제공하고 위치 미확인 상태를 유지한다.
숙소 미정 요청은 검증된 후보 선택 후 초안으로 전환한다. 미확인 가격·재고·예약 가능 여부·이용 시각을 생성하지 않는다. 제공자 기본 이용 시각, 사용자 확정 시각, 미정 상태를 구분한다. 예약 메모를 포함한 숙박 데이터는 기본 비공개이며 실제 예약·결제는 범위 밖이다.
적용 시 최신 여행 기간·숙박 충돌·경로 제약을 재검증한다. 초안의 기준 일정이 바뀌었거나 기존 숙소를 교체할 때는 변경 내용을 다시 확인받고, 적용 요청의 고유성을 보장해 재시도 중복을 방지한다. AI 장애 시 기존 수동 등록 흐름을 유지한다.

## End-to-end planning decisions
기획안 19~23절을 기본 사용 흐름으로 삼는다. 날짜 미정 Trip은 초안과 미배치 장소를 보관하고, 날짜 설정 후 TripDay와 숙박 날짜를 확인한다. 준비 완료는 사용자가 정한 상태이며 모든 정보·예약 검증 완료를 뜻하지 않는다. 자동 여행 시작·완료는 수행하지 않는다.
일정에는 장소 방문 외에 식사·휴식·짐 보관·여유시간을 표현하는 활동 항목을 둔다. 장소 미정 활동도 시간을 차지하되 관련 이동은 미확인으로 둔다. 시간 계산은 이동·활동·여유를 중복 없이 합산하고 실제 조회값·사용자 계획값·미확인을 구분한다. 체크인 가능 범위·체크아웃 마감·사용자 목표 도착을 서로 다른 제약으로 다룬다.
AI 변경 초안은 대상 여행 버전, 변경 범위, 변경 전후, 고정 조건, 의존하는 변경 묶음을 가진다. 부분 선택 후 재검증하고 최신 여행 버전과 일치할 때 명시 적용한다. 적용은 원자적이며 재시도에 멱등성을 보장한다. 되돌리기는 계획 변경만 복원하며 이후 편집과 충돌하면 영향 비교 후 확인받는다. Visit·Photo와 실제 완료 상태는 복원으로 덮어쓰지 않는다.
여행 상세는 전체·날짜별·숙소 보기로 구성한다. 전체는 날짜별 지역·주요 일정·숙소·이동·충돌·미확인을 요약하고 편집 대상으로 연결한다. 미배치 항목과 숙소 미정은 저장을 막지 않는다.
여행 중에는 현재 시각·출발점 수정 후 남은 시간과 충돌을 조회 가능한 범위에서 갱신한다. 자동 대체 코스는 후속이다. 비회원 초안은 기기 저장 상태를 표시하고 가입 후 중복 없이 가져온다. 오프라인 저장 일정과 완료·메모 대기 변경은 서버 저장과 구분하며 재접속 충돌을 조용히 덮어쓰지 않는다.
출시 순서는 흐름 설계 → 수동 내부 알파 → AI 검증 → 기록·캐릭터를 포함한 외부 베타 → 후속 확장이다. 실시간 3D와 영상 제작 도구는 베타 필수 의존성이 아니다. 기존 기간 예상은 재산정 대상으로 두며 외부 서비스의 최신 정책·가격·연동 가능성은 구현 전 별도 확인한다.

## Recommendation selection state
추천 응답과 확정 Trip을 분리한다. 추천 결과 ID·방문 항목 ID를 기준으로 선택 집합을 관리하고 최초 검증된 결과에서 모든 항목을 선택한다. 대안 후보와 숙소 제약은 별도 집합이다. 날짜 탭·상세 이동은 선택 집합을 변경하지 않는다. 전체/일자별 부분 선택과 전체 날짜 선택 수를 같은 상태에서 계산한다.
선택 변경은 체류 합계만 즉시 계산하고 영향을 받은 이동 구간을 미확인 또는 갱신 필요로 표시한다. 경로 조회는 별도 사용자 동작이나 적용 전 검증으로 묶는다. 적용은 현재 여행 버전·기존 항목·고정 조건을 재검증하고 결과/방문 항목의 적용 이력으로 중복을 방지한다. 실패 시 결과와 선택을 보존한다. 재추천·교체가 선택을 초기화하는 경우 사용자에게 영향을 먼저 확인받는다.
시각 구조는 트리플 공개 웹에서 관찰한 질문/결과 구성을 참고하며, 색·서체 체계는 2026-09-09 리뉴얼로 확정한 ‘클린 앱 표준’(PRODUCT.md 브랜드 결정, DESIGN.md 토큰)을 따른다. 모바일 결과는 지도→날짜 탭→선택 가능한 카드→고정 담기, PC는 지도와 목록의 병렬 배치를 제안한다. 상세 기준은 기획안 25절과 분석 문서를 따른다. 이번 추가는 후속 구현 설계다.
