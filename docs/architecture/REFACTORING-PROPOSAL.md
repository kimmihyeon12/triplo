# 아키텍처 최신성 점검 및 리팩터링 제안

- 작성일: 2026-09-30
- 검토 기준: Git `886d6c1` 및 현재 작업 트리
- 상태: **검토 제안. 구현·개발 순서 변경 미승인, 미착수.**
- 범위: 아키텍처 문서와 구현 비교, 상태관리·중복 코드·조회 구조 개선

## 1. 결론

기능별 폴더, 저장소 인터페이스, 순수 계산 함수, Signals 기반 상태관리는 유지할 만하다. 우선 개선 대상은 저장 기준 버전의 소유권, 정산 화면에 집중된 업무 상태, 여행 상세의 반복 UI다.

[ARCHITECTURE.md](ARCHITECTURE.md)는 최초 점검에서 현재 구현과 과거 계획이 섞여 있었다. **2026-09-30 후속 요청으로 원본의 사실 설명을 최신화했다.** 아래 2절 표는 갱신 전 차이와 수정 근거를 보존한다. 구현이 설계 원칙을 따르지 않는 부분은 원본에도 남은 차이로 명시했으며, 코드가 있다는 이유로 원칙을 자동 변경하지 않았다.

이 문서는 제안과 조사 기록이다. 후속 작업에서 아키텍처 원본의 사실 설명을 갱신했으며, 기획안·OpenSpec·개발 순서는 변경하지 않았다. R1~R6 중 채택할 항목이 정해지면 관련 원본과 OpenSpec 제안·설계·요구사항·작업을 함께 갱신한다.

## 2. 아키텍처 문서 최신성 확인

### 2.1 현재 코드와 일치하는 내용

- Angular 21, 기능별 `feature/ui/data/model/util` 구성.
- `signalState` 기반 여행·AI·채팅 상태 서비스와 작은 UI 상태의 `signal` 사용.
- `TripWorkspace`의 `providers: [TripEditorStore]`와 하위 장소·숙소 편집 경로의 인스턴스 공유.
- 모델·순수 계산과 저장 구현 분리, 기능 경계·순환 참조 검사.
- `provideZonelessChangeDetection()` 등록.
- `/stats`의 방문 지도와 `/stats/details`의 일반 통계 경로.

| 순서 | 항목 | 목적 | 변경 위험 |
| --- | --- | --- | --- |
| R1 | 여행 저장 기준 버전을 명시 | 편집 데이터와 충돌 검사 기준을 함께 추적 | 높음: 저장 계약과 모든 호출자 영향 |

## 4. 상세 제안

### R1. 여행 저장 기준 버전을 편집 스냅샷에 포함

**관찰**

`TripRepository.save(trip)`는 기준 서버 버전을 인자로 받지 않는다. `SupabaseTripRepository`의 내부 `versions` 맵이 버전을 관리한다. `PendingDraft.version`은 클라이언트 저장 순번이며 서버 버전이 아니다.

현재 `list()`는 이미 기억한 버전을 올리지 않도록 보완되어 있다. 이전 감리의 목록 재조회 결함이 그대로 남았다고 단정하지 않는다. 이 제안은 호출 순서에 의존하는 계약을 명시적으로 바꾸기 위한 것이다.

**변경 방향**

- 편집용 조회 결과를 `{ trip, serverVersion }` 형태로 전달하는 계약을 검토한다.
- 저장에 `expectedVersion`을 명시하고 저장 성공 결과로 새 서버 버전을 반환한다.
- 미저장 초안에 기준 서버 버전과 클라이언트 편집 순번을 별도로 보관한다.
- 같은 여행의 대기 저장은 앞선 저장 성공으로 받은 버전을 어떻게 이어받는지 정의한다. 동료 변경 후의 충돌을 임의로 최신 버전으로 재시도하지 않는다.
- 신규 여행, 삭제, 서버본 다시 읽기, 계정 변경, 로컬 테스트 구현까지 계약을 맞춘다.
- 업무 모델 `Trip`에 저장소 전용 필드를 무조건 추가하기보다 편집 스냅샷으로 감싸는 방안을 우선 검토한다.

**주요 파일**

[TripRepository](../../app/src/app/features/trips/data/trip-repository.ts), [Supabase 저장소](../../app/src/app/features/trips/data/supabase-trip-repository.ts), [편집 상태](../../app/src/app/features/trips/data/trip-editor-store.ts), [미저장 초안](../../app/src/app/features/trips/data/pending-draft-registry.ts). 실제 착수 시 모든 저장 호출자와 로컬 구현을 함께 조사한다.

**완료 검증**

- v1 편집 중 서버 v2 변경 → 충돌 → 목록 조회·이동·재시도에도 동료 변경 보존.
- 연속 편집 A/B 저장 시 A 성공이 B 초안을 제거하지 않음.
- 계정·여행 전환 뒤 이전 응답이 현재 화면 상태를 변경하지 않음.
- 신규 여행 저장과 저장 응답 유실 후 재시도 정책 검증.
- 단위 테스트 외에 실제 DB 동시 요청 검증을 별도로 수행.

### R2. 정산 업무 상태를 ExpensesStore로 분리

**관찰**

`Expenses`는 약 370줄이며 조회, 요청 번호, 가계부 데이터, 저장 실패 복구, 충돌 후 폼 갱신, 참여자·지출·수령 작업을 조정한다. `LedgerSaver`는 저장 직렬화 일부를 맡지만 전체 상태 소유자는 화면이다. 여행 편집 스토어에도 직접 의존한다.

**변경 방향**

- 화면 또는 여행 정산 경로 범위의 `ExpensesStore`를 두고 데이터·조회·저장·오류·충돌 상태를 관리한다.
- `load`, 지출 저장, 참여자 변경, 수령 처리 등 명명된 메서드로 변경한다. 외부에는 읽기 신호를 제공한다.
- 탭·단순 펼침 상태는 화면에 남긴다. 편집 폼의 기준 데이터와 충돌 후 재입력 정책은 저장 상태와 함께 관리한다.
- 여행 ID·참여자·예상 비용 등 정산에 필요한 조회 계약을 정하고 `TripEditorStore` 전체에 대한 의존을 줄인다.
- 기존 `LedgerSaver`는 새 스토어 내부 실행기로 유지할지 통합할지 한 가지로 정해 책임 중복을 피한다.

**완료 검증**

- 여행 A 조회·저장 중 B로 이동하면 A 결과가 B 상태를 덮지 않음.
- 조회 실패를 빈 가계부·0원으로 보여주지 않음.
- 이중 클릭, 부분 저장 실패, 충돌 후 최신 폼 반영, 삭제된 지출의 편집 종료 유지.
- 지출 합계·분담·수령·정산 복사 결과가 기존과 동일.

### R3. 여행 상세와 지도 링크의 반복 UI 추출

**관찰**

여행 상세는 HTML 약 1,030줄, TS 약 554줄이다. 장소·숙소 행에서 지도 링크와 클릭 영역·아이콘·설명이 반복된다. 같은 지도 링크는 AI 일정과 숙소 목록에도 있다. 크기 자체보다 같은 변경을 여러 곳에서 반복해야 하는 비용이 문제다.

**변경 방향**

- 지도 링크 묶음을 `places/ui`의 입력 중심 컴포넌트로 추출한다. 기존 링크 생성·실행 규칙을 재사용한다.
- 일정 장소 행과 숙소 행을 각각 `trips/ui`로 추출한다. 서로 다른 업무 규칙은 유지한다.
- 행은 데이터를 입력받고 선택·이동·수정·삭제 의도를 출력한다. 저장소를 직접 주입하지 않는다.
- 일정 추가 메뉴와 전체 요약은 상태 소유가 명확할 때 별도 추출한다.
- 기존 DOM 식별자, 지도 선택 연결, 라우터 파라미터, 클릭 영역, 키보드 동작을 보존한다.

**완료 검증**

- 모바일·데스크톱에서 장소/숙소 선택, 지도 열기, 순서 변경, 수정·삭제 흐름 비교.
- 메뉴 포커스, 접근성 이름, 긴 제목, 위치 없는 항목, 빈 일정, 고정 시간 충돌 표시 확인.
- 외형을 동일하게 유지하는 추출 단계와 디자인 변경 단계를 분리.

### R4. 방문 지도는 여행을 한 번 읽고 집계

**관찰**

`VisitMapPage.load()`는 방문 집계·저장 장소·방문 지점을 병렬 요청한다. `LocalVisitStats`와 `SavedMapPlaces`는 각각 `TRIP_REPOSITORY.list()`를 호출한다. 운영에서는 동일 화면 진입에서 전체 여행 조회가 반복될 수 있다.

**변경 방향**

- 지도 조회 서비스가 여행 목록을 한 번 읽고 기존 순수 집계 함수를 호출한다.
- 방문 수·마커·방문 지점을 같은 스냅샷과 기준 날짜에서 계산한다.
- 새로고침·필터 변경·여행 저장 후 재조회 조건을 명시한다.
- 먼저 단일 로딩 흐름의 중복을 제거한다. 전역 캐시 도입은 별도 필요성이 확인될 때 검토한다.

**완료 검증**

- 한 번의 지도 데이터 로딩에서 여행 목록 조회 1회.
- 기존 집계와 동일한 지역 수·방문 수·제외 사유·마커 결과.
- 빈 데이터·실패·필터 변경·늦은 응답 처리와 3D 자원 해제 유지.

### R5. 채팅의 적용·되돌리기 실행 책임 분리

**관찰**

`TravelChatStore`는 약 420줄로 대화 진행, 로컬 명령, 장소 검증, 초안 변환, 일정·정산 적용, 되돌리기 상태를 조정한다. 한 가지 변경의 영향 범위를 파악하기 어렵다.

**변경 방향**

- 스토어는 대화 메시지·요청 진행·오류·추천 상태를 소유한다.
- 초안 적용과 되돌리기는 명시적인 입력·결과 계약을 가진 실행 서비스로 분리한다.
- 기존 순수 명령 해석과 초안 계산 함수는 재사용한다.
- 일정과 정산의 저장·충돌 규칙을 각각 유지하고 명령 성공 뒤에만 완료 메시지와 되돌리기 상태를 확정한다.
- 사용자·여행·요청 식별을 함께 전달해 전환 뒤 늦은 결과를 반영하지 않도록 한다.

**완료 검증**

- 로컬 명령과 모델 호출의 기존 분기 유지.
- 일정·정산 적용 실패를 성공으로 표시하지 않음.
- 적용 후 다른 수정이 생긴 경우 되돌리기 충돌 처리.
- 대화 초기화·계정/여행 전환 중 늦은 결과가 새 대화에 들어오지 않음.

### R6. 공통 브라우저 기능 위치와 비동기 처리 규칙 정리

**관찰**

정산·초대 등이 텍스트 복사를 위해 `places/data/map-links.ts`의 `copyText`에 의존한다. 요청 번호·AbortController·세션 세대 번호도 기능별로 사용하고 있다.

**변경 방향**

- 클립보드 복사는 업무 무관한 브라우저 기능으로 이동한다. 브라우저 의존을 금지한 `shared/util`에는 두지 않고 `core` 등 허용 계층에 배치한다.
- 비동기 규칙은 먼저 문서로 통일한다: 조회 취소/늦은 결과 폐기, 쓰기 순서 보장, 전환 시 세션 검사, 실패 종류 구분.
- 여러 호출부의 취소·재시도 의미까지 같을 때만 작은 공통 도구로 추출한다.

**완료 검증**

- 클립보드 사용 불가·권한 거부 시 실패 안내 유지.
- 기능 경계·순환 참조 검사 통과.
- 공통 도구로 바꾼 호출부의 전환·취소·실패 회귀 검증.

## 5. 검증 결과와 한계

이번 제안 작성 직전 같은 대화에서 현재 코드에 실행한 결과:

| 검사 | 실제 결과 | 범위 |
| --- | --- | --- |
| `npm test` | 76개 파일, 655개 테스트 통과 | 구성된 단위 테스트 |
| `npm run lint` | 214개 모듈의 경계·순환 참조 검사 통과 | 정의된 의존성 규칙 |
| 같은 lint의 대비 검사 | 9개 조합 통과 | 전체 화면 접근성 인증 아님 |

이번 문서 작성에서는 빌드·E2E·원격 DB·외부 AI 실호출을 추가 수행하지 않았다. 위 검사 통과는 리팩터링 구현 완료나 운영 동시성 보장을 뜻하지 않는다. 파일 줄 수는 검토 시점의 참고값이다.

리팩터링 착수 시 변경에 맞는 단위 테스트·경계 검사·빌드를 수행한다. 화면 추출은 별도 테스트 앱에서 모바일·데스크톱 E2E로, 저장 계약 변경은 실제 DB 충돌·동시 요청으로 확인한다.
