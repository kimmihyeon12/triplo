# 여행 자동생성: 예산·요금 기준·체류시간

## 사용 흐름

1. 부산·서울 등 시·도 전체 또는 시·군·구를 고른다. 전체 지역은 검색 결과 맨 위에 표시한다.
2. 본인 포함 인원과 여행 전체 기간 예산을 입력한다. 예산은 선택이며 1인 기준과 전체 인원 기준을 구분한다.
3. 추천 결과는 1일차·2일차별 시간순 코스로 보여 준다(2026-09-30 [코스 변경](../openspec/changes/add-ai-course-plan/proposal.md)). 일차를 바꾸면 장소가 그날 코스 끝으로 이동하고 추천 시각은 미정이 된다.
4. 장소별 예상 금액, 요금 기준(단가·인원·횟수·포함 상품), 추천 체류시간을 확인한다.
5. 선택한 항목 비용만 합산하고 가계부와 같은 분류(식비·숙박·관광·액티비티·쇼핑·기타)로 나눈다. 숙소 비용은 포함하고 교통비와 미정 항목은 포함하지 않는다. 예산 여유·초과를 알리지만 예산 내 여행을 보장하지 않는다.
6. 담기를 누르면 예상 범위의 상한을 기존 계획 금액·체류시간에 넣고 AI 추정·범위·계산 기준을 메모에 보존한다. 실제 지출을 자동 생성하지 않는다. 입력 예산은 이번 추천의 조건이며 가계부 예산을 변경하지 않는다.

현재 장소 검색 제공자는 실제 요금을 반환하지 않는다. 모든 생성 금액과 체류시간은 **AI 추정**이다. 지도 검색 성공은 장소 존재 확인일 뿐 요금 확인이 아니다. 모델이 만든 출처 URL이나 확인일은 공식 근거로 받아들이지 않는다. 실제 확인된 요금을 제공하려면 별도 출처 조회·검증이 필요하다.

## ai-plan API 변경

기존 `POST /functions/v1/ai-plan` 요청에 다음 선택 항목을 추가한다. 기존 인증·할당량·오류 코드는 유지한다.

| 필드 | 값 | 생략 시 |
|---|---|---|
| partySize | 정수 1~100 | 1 |
| budget | null 또는 정수 0~100000000, 원 | null |
| budgetBasis | person / group | group |

인원·예산이 잘못되면 모델 호출·할당량 차감 전 HTTP 400 `invalid_request`를 반환한다. `person` 예산은 인원과 곱해서 전체 예산도 모델에 전달한다.

응답은 기존 `{ content: string, remaining: number }` 봉투를 유지한다. content의 JSON 예시(가상 값):

```json
{
  "items": [{
    "day": 1,
    "order": 2,
    "name": "예시 식당",
    "kind": "식사",
    "start": "12:00",
    "moveToNext": { "mode": "도보", "minutes": 10 },
    "estimate": {
      "cost": {
        "min": 15000,
        "max": 20000,
        "basis": "person",
        "quantity": 1,
        "assumption": "성인 식사 1인분"
      },
      "stay": { "min": 45, "max": 60, "reason": "여유 있는 식사" }
    }
  }]
}
```

- person: 단가 × 인원 × 1인당 이용 횟수.
- group: 일행 전체 단가 × 이용 횟수. 인원을 다시 곱하지 않는다.
- room_night: 객실당 1박 단가 × 객실 수·박 수의 곱. 별도 숙박 후보를 생성하는 기능은 이번에 추가하지 않는다.
- cost 또는 stay가 null이면 미정이다. 이전 응답처럼 estimate가 없어도 장소 목록은 정상 표시한다.
- 단가 0~10000000원, 수량 1~100, 체류 5~1440분의 정수 범위와 min ≤ max를 검사한다. 산정 가정·이유가 없거나 범위가 잘못되면 해당 값만 미정 처리한다.
- 계산된 항목 금액이 DB 정수 상한 2147483647원을 넘으면 미정으로 처리해 전체 여행 저장 실패를 방지한다.

## 통계와 저장

시·도 전체 선택은 시·도 코드만 저장한다. 방문 통계의 시·군·구는 실제 장소 주소를 우선하며 주소가 없으면 임의 구를 만들지 않는다. 기존 시·군·구 선택과 기존 저장 여행의 데이터는 유지한다.

DB 변경 없이 기존 `estimated_cost`, `stay_minutes`, `memo`를 사용한다. 추정 범위·근거는 메모로 유지하고 구조화된 범위 필드를 DB에 추가하지 않는다. 기존 비용·시간 편집에서 사용자가 계획값을 바꿀 수 있다.

실행 결과는 검증을 마친 뒤 아래에 기록한다. 브라우저 테스트는 운영 앱과 분리한 test 구성·픽스처를 사용한다. 실제 Gemini 생성 품질과 실제 요금 정확성을 검증하는 테스트는 아니다.

## 코스 응답 필드 (2026-09-30)

- `kind`: 관광·액티비티·식사·카페·쇼핑·기타·숙소. 이전 라벨 "장소"는 관광으로 읽는다.
- `order`: 그날 방문 순서(1부터). 모두 1 이상 정수이고 겹치지 않을 때만 쓰고, 아니면 응답 순서를 쓴다.
- `start`: 추천 도착 시각 `HH:mm`. 형식이 틀리거나 앞 항목보다 이르면 미정이다.
- `moveToNext`: 다음 항목까지 `{mode: 도보|대중교통|자가용|택시, minutes: 1~600}`. 마지막 항목은 null.
- 숙소는 그날 마지막 항목이며 `room_night` 1박 요금을 쓴다. 담을 때 숙박으로 만든다.
- 필드가 없는 이전 응답도 받아서 순서대로 시각 없이 표시한다.
- 요청의 `startDate`(선택, `YYYY-MM-DD`, 실제 날짜만 허용)가 있으면 프롬프트에 일차별 날짜·요일을 넣는다. 잘못된 값은 400 `invalid_request`.
- 응답 항목의 `closed`(선택): `{onDay: boolean, note: string}` 또는 null. 모르는 휴무는 null이며 추측으로 채우지 않도록 지시한다. 화면에는 AI 추정으로 보이고 저장은 메모에만 한다.
- 0원 요금은 "무료"로 표시한다. 합계 칸은 금액 계산이라 0원을 그대로 쓴다.
