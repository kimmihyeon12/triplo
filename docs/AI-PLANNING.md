# AI 일정 만들기 연결 가이드

이 문서는 AI 일정 만들기가 어떤 모델을 어떻게 부르는지, 왜 그렇게 정했는지 기록한다. 2026-09-10 작성, 2026-09-17 로컬 LLM에서 Gemini로 교체.

## 현재 구성 (2026-09-17)

```text
브라우저 → Supabase Edge Function(ai-plan) → Gemini
             로그인 확인 · 입력 검증 · 키 보관
```

모델은 **Google Gemini `gemini-3.5-flash-lite`** 다. 무료 등급으로 하루 500회까지 쓸 수 있고 카드 등록이 필요 없다.

**모델 키는 브라우저에 두지 않는다.** Supabase Edge Function의 비밀값으로만 있다. 브라우저가 보내는 것은 사용자가 고른 조건뿐이며, 지시문과 모델 이름은 서버가 갖는다. 요청을 바꿔 모델에게 다른 일을 시키지 못하게 하기 위해서다.

로그인하지 않은 요청은 401로 막는다. 키를 숨기는 것만으로는 아무나 쓰는 것을 막지 못한다.

호출하는 부분은 `AI_PLAN_PROVIDER` 토큰 뒤에 있다. 다른 모델로 바꿀 때 Edge Function의 `index.ts`만 고치며 화면·검증·테스트는 그대로 쓴다.

### 설정 절차

```powershell
# 1. Supabase 로그인 (브라우저가 열린다)
npx supabase login

# 2. 모델 키를 서버 비밀값으로 등록
npx supabase secrets set GEMINI_API_KEY=<aistudio.google.com/apikey 에서 받은 키> --project-ref wslqgfetdwcmqeztixvs

# 3. 함수 배포
npx supabase functions deploy ai-plan --project-ref wslqgfetdwcmqeztixvs
```

모델을 바꾸려면 `GEMINI_MODEL` 비밀값을 함께 등록한다. 없으면 `gemini-3.5-flash-lite`를 쓴다.

### 파일 구성

| 파일 | 역할 |
| --- | --- |
| `supabase/functions/ai-plan/index.ts` | Gemini 호출. 키와 모델 이름을 환경변수에서 읽는다 |
| `supabase/functions/ai-plan/handler.ts` | 인증·입력 검증·오류 구분. 앱 테스트에서 그대로 검증한다 |
| `supabase/functions/ai-plan/prompt.ts` | 지시문과 프롬프트 조립 |
| `app/.../data/edge-ai-provider.ts` | 함수를 부르고 응답을 우리 형식으로 바꾼다 |

## 왜 로컬 LLM을 접었나

RTX 3090 PC에 Ollama를 올려 `qwen3.6:latest`(23GB)·`glm-4.7-flash`(19GB)·`qwen3.5:9b`를 시험했다. 연결은 성공했으나 **한국 지역 지식이 부족해 쓸 수 없었다.**

| 요청 | 모델이 낸 답 | 문제 |
| --- | --- | --- |
| 경주 2일 | 월정사 | 평창에 있다 |
| 경주 2일 | 강원랜드 | 정선에 있다 |
| 경주 2일 | 대동강 | 북한에 있다 |
| 경주 2일 | 경주역 | 관광지가 아니다 |
| 강릉 2일 | 오죽헌을 '고려 시대 건축물'이라 설명 | 조선 시대다 |

프롬프트에 '고유명사만 적는다'는 규칙과 예시를 넣자 행위 설명(`해변 산책`)은 사라졌지만, 지역을 틀리는 문제는 남았다. 이것은 추론 능력이 아니라 아는가 모르는가의 문제라 프롬프트로 고칠 수 없다.

또 요청한 구성(하루 장소 2 + 식사 1)을 지키지 못해 여섯 개를 전부 `장소`로 내는 경우가 있었다.

## 모델 비교 결과 (2026-09-17 실측)

같은 조건(경주 2일 / 통영 2일 / 전주 1일)을 세 모델에 보내 비교했다.

| | 로컬 qwen3.6 | Gemini Flash-Lite | Gemini Flash |
| --- | --- | --- | --- |
| 경주 결과 | 월정사·경주역 등 오류 | 불국사·석굴암·대릉원 | 대릉원·불국사·첨성대 |
| 구성 지킴 | 식사 0개 | 6/6, 식사 2 | 6/6, 식사 2 |
| 응답 시간 | 40초 | **1.2초** | 6~10초 |
| 무료 한도 | 없음 | **500회/일** | 20회/일 |

Flash-Lite가 하루 500회에 1.2초로 가장 실용적이라 이것을 골랐다. Flash가 식당 선택은 조금 나았으나(Flash-Lite는 `교동법주`·`황리단길`을 식사로 분류) 하루 20회로는 쓸 수 없다. 그 차이는 카카오 장소 검색 대조가 보완한다.

## 무료 등급의 조건

- **하루 500회**를 넘으면 `429`가 오고 요청이 실패한다. 카드를 등록하지 않으므로 과금될 경로가 없다. 한국 시간 오후 4~5시경(태평양 자정) 초기화된다.
- **보낸 데이터가 구글의 모델 개선에 쓰일 수 있다.** 이 앱이 보내는 것은 지역·날짜·동행·취향뿐이며 여행 기록이나 사진은 보내지 않는다. 그래도 실제 사용자에게 열 때는 이 점을 고지하거나 유료 등급으로 올려야 한다.
- 무료 모델과 유료 모델이 따로 있는 것이 아니다. 같은 모델을 하루 몇 번까지 공짜로 쓸 수 있느냐의 차이다.

## 남은 일

하루 500회는 앱 전체가 나눠 쓴다. 한 사람이 몰아 쓰면 나머지가 못 쓴다. 지금은 제한을 두지 않았다. 친구 몇 명이 쓰는 규모에서는 문제되지 않지만, 쓰는 사람이 늘면 사용자별 하루 횟수 제한을 `handler.ts`에 넣어야 한다.

## 프롬프트 설계

모델에게 보내는 요청은 [prompt.ts](../supabase/functions/ai-plan/prompt.ts)에 있다. 두 부분으로 나뉜다.

- `SYSTEM_PROMPT`: 이름·분류·선정 규칙. 실측에서 이 지시가 없으면 '해변 산책' 같은 행위 설명을 이름 자리에 넣거나 같은 문장을 반복했다.
- `userPrompt()`: 사용자가 고른 조건을 문장으로 만든다.

**사용자가 적은 추가 요청을 맨 앞에 둔다.** 뒤에 붙이면 기본 구성(하루 장소 5·식사 3·카페 2)에 눌려 '롯데월드 안 맛집만'이라고 적어도 관계없는 장소가 따라온다.

요청이 종류·개수·범위를 정했으면 **기본 구성을 아예 보내지 않는다**(`noteSetsScope`). 기본 개수가 남아 있으면 모델이 그 숫자를 채우려고 요청에 없는 장소를 넣는다. 판정은 '만·말고·빼·제외·없이·위주·중심'과 숫자가 붙은 개수 표현으로 한다. '사진 찍기 좋은 곳' 같은 취향 문장까지 범위 지정으로 보면 결과가 너무 적어진다.

실측 확인(2026-09-17): "롯데월드만 갈거야. 롯데월드 안에 있는 맛집만 추천해줘"에 롯데월드와 스쿨푸드 롯데월드점 두 곳만 나왔다. 관계없는 장소는 없었다. 다만 "하루에 2끼"는 지켜지지 않았는데, 모델이 롯데월드 안 식당을 한 곳만 확실히 알기 때문이다. 이런 경우 억지로 개수를 채우게 하면 지어낸 이름이 나오고 카카오 대조에서 걸러진다.

## 앱 구현·검증 기준

- 모델에게는 **장소 이름·일차·분류만** 받는다. 좌표·주소·영업시간·설명은 받지 않는다. 모델이 쓰는 설명은 사실 오류가 잦다.
- 받은 이름은 카카오 장소 검색으로 대조한다. 찾은 것만 확인된 장소로 두고 좌표·주소·분류를 검색 결과에서 가져온다. 찾지 못한 이름은 지우지 않고 '직접 확인 필요'로 남기되 선택할 수 없게 한다.
- 대조할 때 **후보 여러 개를 받아 이름이 실제로 맞는 것만 고른다**. 첫 번째 후보를 그대로 믿으면 검색이 돌려준 '가장 비슷한 가게'가 엉뚱한 동네에서 확정 장소로 들어온다. 이름 비교는 띄어쓰기·괄호·점을 지운 뒤 한쪽이 다른 쪽에 통째로 들어 있는지로 본다. '롯데월드'와 '롯데월드 어드벤처'는 같게 보고, '자이언트디거'와 '중국성 서초점'은 다르게 본다.
- **정확히 같은 이름을 먼저 고른다.** 부분만 겹치는 후보를 순서대로 집으면 '롯데월드'를 물었을 때 앞에 있는 '롯데월드 주차장'이 확정된다. 이름은 롯데월드로 남고 좌표만 주차장이 되어 사용자가 잘못된 줄 알 수 없다. 주차장·매표소·정류장 같은 부속 시설은 이름이 겹쳐도 그 장소가 아니므로 아예 받지 않는다.
- **지역이 여럿이면 차례로 찾아본다.** 첫 지역으로 고정하면 '강릉 속초관광수산시장'이라는 검색어가 되어 뒤쪽 지역의 장소를 영영 확인하지 못한다. 정확히 맞는 것을 찾으면 남은 지역은 뒤지지 않는다.
- 응답은 JSON Schema로 제한한 뒤 앱에서 다시 검사한다. Gemini는 `additionalProperties`를 모르므로 스키마에 넣지 않는다(넣으면 400).
- 실패는 연결 실패·시간 초과·하루 한도 초과·빈 결과로 나눠 알리고 입력 조건을 보존한다. 샘플로 바꿔치지 않는다.
- 테스트 앱은 외부 호출 없는 `FixtureAiProvider`로 검증하고 실제 호출 검사는 별도로 기록한다.

## 대화형 챗봇 (2026-09-17 기획, 미구현)

대화형 여행 탐색 챗봇도 같은 모델 `gemini-3.5-flash-lite`를 쓴다. 대화는 한 여행을 계획하는 동안 여러 번 호출되므로 무료 하루 500회 한도가 상위 모델의 품질 차이보다 중요하다. 상위 Flash는 하루 20회라 대화에 쓸 수 없다.

호출 경로는 `ai-plan`과 별개의 Edge Function `ai-chat`으로 둔다. 지시문·응답 형식·검증 규칙이 다르고 한쪽 배포가 다른 쪽을 멈추게 하지 않아야 한다. 키 보관과 로그인 확인 방식은 같다.

**Function Calling은 쓰지 않는다.** 모델이 등록 함수를 직접 부르게 하면 카카오 장소 검색 대조를 사이에 넣기가 구조적으로 어색해지고, 기획안 20절의 AI 단독 반영 금지와도 어긋난다. 모델은 구조화된 JSON 초안만 돌려주고 등록은 사용자 확인 뒤에 앱이 수행한다.

위 구현·검증 기준은 챗봇에도 그대로 적용한다. 다만 **대화 중 안내는 예외**다. 영업시간·요금·예약 여부는 모델이 답할 수 있으며, 확인된 사실과 구분해 표시하고 네이버·카카오 링크를 함께 제공한다(2026-09-17 사용자 결정). 이 값들은 일정에 저장되지 않으므로 저장 데이터의 검증 원칙과 충돌하지 않는다.

대화 한 세션의 호출 상한은 20회다. 아래 '남은 일'의 사용자별 제한과 함께 `handler.ts`에서 다룬다.

설계 결정과 화면 배치는 [설계 문서](superpowers/specs/2026-09-17-travel-chat-design.md)와 기획안 35절에 있다.

## 검증 기록

- 2026-09-17 브라우저 직접 호출로 먼저 확인: 경주 1박 2일 요청에 8초, 6건 전부 위치 확인, 담은 뒤 지도에 마커 3개와 안내선 표시. `토함산식당`처럼 실제 식당을 골랐다.
- 2026-09-17 Edge Function 배포: `ai-plan` 함수 ACTIVE, `verify_jwt: true`, `GEMINI_API_KEY` 비밀값 등록 확인. 인증 없는 요청은 401로 막힌다(curl로 확인).
- 2026-09-17 사용자 보고: "롯데월드 안에 식당 3곳"에 롯데월드 2건과 중국성(서초)이 나왔다. 검색어가 `서울 중국성`으로 조립되어 서울 전역에서 찾은 뒤, 그 결과를 이름 확인 없이 확정한 것이 원인이다. 이름 대조를 넣어 고쳤다(단위 테스트로 재현·확인). 모델이 롯데월드 안 상호를 얼마나 아는지는 별개 문제이며, 이제 모르는 이름은 확정되지 않고 '직접 확인 필요'로 남는다.
- 로컬 Ollama 구성(Tailscale `100.124.45.75:11434`)은 품질 미달로 접었다. 필요하면 `git log`에서 `OllamaProvider`를 찾을 수 있다. 브라우저가 Gemini를 직접 부르던 `GeminiProvider`도 같은 자리에 있다.
