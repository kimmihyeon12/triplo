# AI 일정 짜기·AI 챗봇 답변 품질 개선 설계: 실제 장소 후보 위에서 정해진 일만 하기

2026-10-01 작성. 요구사항은 [기획안](../../기획안-v0.1.md) 35절(챗봇)과 '자동생성 시간순 코스와 분류 통일' 절(일정 짜기)에, 기존 설계는 [챗봇 설계](2026-09-17-travel-chat-design.md)·[코스 설계](2026-09-30-ai-course-plan-design.md)에 있다. 이 문서는 그 위에 얹는 변경만 다룬다.

## 1. 목적과 문제

사용자가 꼽은 문제(2026-10-01):

1. **장소가 엉뚱하거나 없다.** 두 기능 모두 모델이 기억으로 장소 이름을 지어 내고 앱이 뒤에서 카카오로 대조한다. 지어낸 이름은 빠지고, 비슷한 이름의 다른 곳이 잡힌다. 일정 짜기에서는 식당이 모두 빠져 어느 날 밥이 없는 일이 있었다.
2. **답이 뻔하고 얕다.** 챗봇 지시문이 "짧고 친근하게"를 요구하고, 모델은 후보 없이 일반론으로 답한다.
3. **정해진 기능을 벗어난다.** "저녁 이후"라고 했는데 하루 전체를 짜거나, 카페 위주 요청에 점심·저녁이 사라지거나, 고른 식당이 한 자리를 대신하지 않고 더해진다. 규칙이 지시문 곳곳에 흩어져 있고 우선순위가 없다.

성공 기준:

- 두 기능이 결과에 내는 장소는 모두 카카오 검색 결과에서 나온 실제 장소다.
- 일정 짜기는 정해진 구성(식사·카페·관광·숙소, 요청 범위)을 지키고, 지키지 못한 자리는 앱이 채우거나 알린다.
- 챗봇 코스 답변은 장소마다 이유 한 줄과 시간대 순서·동선을 갖춘다.
- 모델(`gemini-3.5-flash-lite`)과 호출 횟수는 그대로다.

## 2. 정한 것과 정하지 않은 것

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 모델 | 그대로 | 사용자 결정(2026-10-01). 상위 모델은 무료 하루 20회라 앱 전체가 쓸 수 없다 |
| 장소 근거 | 앱이 카카오 검색으로 후보를 먼저 모아 모델에 준다. 모델은 후보 번호로 고른다 | 엉뚱한 장소를 구조적으로 없앤다. 좌표·주소는 지금처럼 검색 결과에서만 가져온다(AGENTS 규칙) |
| 규칙 집행 | 지시문은 우선순위가 있는 규칙표로 다시 쓰고, 지켜야 하는 규칙은 앱이 결과를 받은 뒤 다시 검사·보정한다 | 작은 모델은 긴 지시문의 뒤쪽 규칙을 놓친다. 지시문만 믿지 않는다 |
| 구글 검색 근거·Function Calling | 쓰지 않는다 | 국내 장소 정확도가 카카오보다 낮다. 검증 단계를 사이에 두기 어렵다(챗봇 설계 3절) |

## 3. 공통: 장소 후보 모으기 (앱)

두 기능이 같은 모듈(`place-candidates.ts`)을 쓴다.

```json
{ "id": "c7", "name": "초당순두부마을", "kind": "meal", "category": "음식점 > 한식 > 두부전문점", "area": "강릉시 초당동" }
```

- `kind`는 앱이 검색 분류로 정한다(`kindFromCategory`). 모델이 분류를 정하지 않는다.
- `area`는 주소의 시군구·동이다. 좌표는 모델에 보내지 않는다. 동선은 `area`로 묶게 한다.
- 이미 그 여행에 있는 장소, 겹치는 장소는 뺀다.
- 검색이 모두 실패하면 빈 목록을 돌려준다. 그러면 두 기능은 지금처럼 이름 방식으로 동작한다(멈추지 않는다).
- 후보는 앱이 들고 있다가 답을 받은 뒤 좌표·주소·장소 ID를 붙인다. 다시 검색하지 않는다.

### 일정 짜기의 후보

지역마다 아래를 찾는다(지역 최대 3곳, 후보 최대 120곳).

| 검색어 | 크기 | 비고 |
| --- | --- | --- |
| 관광명소, 가볼만한곳 | 15씩 | 관광 |
| 맛집 | 15 | 식사 |
| 카페 | 15 | 카페 |
| 체험 | 10 | 액티비티 |
| 시장 | 10 | 쇼핑 |
| 호텔·펜션 | 10 | 당일치기면 찾지 않는다 |
| 취향 낱말(사진→가볼만한곳, 먹방→맛집 등) | 10 | 3절 챗봇 표와 같은 표 |

꼭 갈 장소는 따로 찾아 `must: true`로 표시한다. 모델은 이것을 반드시 넣고, 빠뜨리면 앱이 넣는다(지금의 `mustGoPlaces`·`pinMeals` 그대로).

### 챗봇의 후보

| 대화 | 지역 |
| --- | --- |
| 여행 상세 | 그 여행의 지역. 질문이 특정 일차를 가리키면 그날 장소 근처 5km |
| 전체 채팅 | 이번 질문, 없으면 최근 대화에서 읽은 국내 지역 이름 |

질문 낱말로 검색어를 고른다(정해진 표만 쓴다). 한 질문에 검색은 최대 4번, 후보 40곳.

| 낱말 | 검색어 |
| --- | --- |
| 맛집·먹방·밥·식당·점심·저녁 | 맛집 |
| 카페·디저트·빵 | 카페 |
| 사진·뷰·전망·풍경 | 가볼만한곳 |
| 야경·밤바다 | 야경 |
| 관광·볼거리·명소 | 관광명소 |
| 체험·액티비티·아이 | 체험 |
| 시장·쇼핑 | 시장 |
| 그 밖(코스 짜줘 등) | 관광명소·맛집·카페 |

지역을 모르면 후보 없이 보낸다. 모델은 지역을 한 번 되묻는다.

## 4. 응답 형식 변경

### 일정 짜기(`ai-plan`)

요청에 `candidates`(위 모양, 최대 120)를 더한다. 서버는 개수·글자 수를 검사한다. 응답 `items`에 `ref`를 더한다.

- 후보를 보낸 요청: `ref` 필수. 보낸 후보에 없는 `ref`, `ref` 없이 이름만 낸 항목은 앱이 버린다. 분류는 후보의 `kind`를 쓴다.
- 후보가 없는 요청(옛 앱, 검색 실패): 지금처럼 이름을 받아 검색으로 대조한다.
- 버린 뒤 모자란 자리는 지금의 하루 최소 구성 보충이 채운다. 이때 근처를 새로 검색하기 전에 쓰지 않은 후보부터 쓴다.

배포 순서: 서버는 후보가 없는 요청을 지금처럼 처리하므로 `ai-plan`을 먼저 배포하고 앱을 배포한다.

### 챗봇(`ai-chat/contract.ts`)

요청에 `candidates`(최대 40)를, 응답 `places` 항목에 `ref`와 `why`(추천 이유, 80자 이내)를 더한다. 검사 규칙은 일정 짜기와 같다.

배포 순서: 앱이 `contract.ts`를 함께 번들해 응답을 다시 검사하므로, 새 앱이 옛 응답도 받게 만든 뒤 **앱을 먼저, `ai-chat`을 나중에** 배포한다(2026-09-30 순서를 바꿨다가 운영 챗봇이 깨질 뻔한 기록).

## 5. 프롬프트 다시 쓰기

### 원칙

1. **역할과 범위를 맨 앞에 한 문단으로 둔다.** 무엇을 하는 기능이고 무엇은 하지 않는지.
2. **규칙에 우선순위를 매긴다.** 충돌하면 위가 이긴다. 지금은 "추가 요청을 먼저 지켜라"와 "식사는 반드시"가 같은 무게로 섞여 있다.
3. **입력을 칸으로 나눠 이름을 붙인다.** `[요청]`, `[후보]`, `[여행]`, `[대화]`. 모델이 어디서 무엇을 읽을지 헷갈리지 않게 한다.
4. **출력 전 확인 목록을 둔다.** 작은 모델은 마지막에 다시 보게 하면 규칙을 더 지킨다.
5. **같은 규칙을 앱이 다시 검사한다.** 지시문은 확률을 올리는 수단이고, 지켜야 하는 것은 코드가 보장한다(아래 표).

### 일정 짜기 지시문(초안)

```text
너는 국내 여행 일정 짜기 기능이다. [후보]에 있는 실제 장소만 골라 날마다 시간순 코스를 만든다.
장소를 새로 지어내지 않는다. 좌표·주소·영업시간·전화번호는 쓰지 않는다.

규칙(위가 먼저다):
1. [요청]이 종류·개수·시간대를 정했으면 그 범위만 짠다. '저녁 이후'면 그 시간대 일정만 넣는다.
2. [꼭 갈 곳]은 반드시 넣는다. 꼭 갈 곳이 식당이면 점심이나 저녁 한 자리를 대신한다. 식사를 늘리지 않는다.
3. 범위를 정하지 않았으면 하루에 식사 2곳(점심 12~14시, 저녁 18~20시), 카페 1곳,
   관광·액티비티·쇼핑을 합쳐 {밀도별 개수}를 넣는다. 아침을 요청했으면 아침(8~9시)도 넣는다.
4. 마지막 날을 뺀 날의 끝에 숙소 1곳. 당일치기면 숙소를 넣지 않는다.
5. 하루 안에서는 같은 area의 후보를 묶는다. 같은 장소를 두 번 넣지 않는다.
6. 휴무·요금·체류시간은 추정이다. 모르면 null로 둔다. 무료인 곳은 0원으로 적는다.

출력 전 확인:
- 모든 항목의 ref가 [후보]에 있는가
- 날마다 1~4번 규칙을 지켰는가
- start가 시간순이고, 앞 항목 + 체류 + 이동이 다음 start를 넘지 않는가
```

분류 정의·이름 규칙·비용 규칙은 지금 문장을 그대로 두되, 후보를 쓰는 요청에서는 이름 규칙 대신 "ref로 고른다"만 보낸다.

### 챗봇 지시문(초안)

```text
너는 국내 여행 앱의 여행 친구 구름이다. 하는 일은 셋이다.
(1) 여행지·코스 추천 (2) 영업시간·요금 같은 참고 정보 안내 (3) 여행과 관계없는 질문 거절.
일정을 직접 바꾸거나 저장하지 않는다. 저장은 사용자가 확인 카드에서 한다.

규칙(위가 먼저다):
1. 장소는 [후보]에서만 ref로 고른다. [후보]에 없는 장소 이름을 쓰지 않는다. 마땅한 곳이 없으면 그렇다고 말하고 다른 테마를 제안한다.
2. 지역·기간을 모르면 한 가지만 묻는다. [여행]·[대화]에 이미 있으면 다시 묻지 않는다.
3. 코스 추천은 한 줄 요약 → 시간대 순서의 코스 → 장소마다 이유 한 줄(why) → 다니는 팁 1~2개로 쓴다. 본문 400~700자.
4. 같은 area끼리 묶어 동선을 짠다. 점심과 저녁 사이에 먼 동네를 오가지 않는다.
5. 이유는 분류·동네·대화 속 취향(혼자, 아이와, 사진)에 근거한다. 맛·분위기를 단정하지 않는다.
6. 영업시간·요금·휴무는 kind=reference로 답하고 미확인 참고 정보임을 밝힌다. 사실처럼 쓰지 않는다.
7. 여행 외 질문은 kind=refusal, 예약·구매 대행은 kind=outside로 짧게.

출력 전 확인:
- places의 모든 ref가 [후보]에 있는가
- 장소마다 why가 있는가
- 묻지 않은 일(정렬·삭제)을 덤으로 하지 않았는가
```

## 6. 앱이 다시 검사·보정하는 것

| 규칙 | 일정 짜기 | 챗봇 |
| --- | --- | --- |
| 후보에 있는 장소만 | ref 검사, 없으면 버림 | ref 검사, 없으면 버림 |
| 분류 | 후보의 kind | 후보의 kind |
| 하루 식사 2·카페 1·관광 최소 | 남은 후보 → 근처 검색 순으로 채움, 못 찾으면 알림(구현됨) | 해당 없음 |
| 고른 식당이 한 자리를 대신 | 구현됨 | 해당 없음 |
| 범위·시간대 요청 | 보충하지 않음(구현됨) | 해당 없음 |
| 당일치기·마지막 날 숙소 없음 | 구현됨 | 해당 없음 |
| why 길이 | 해당 없음 | 80자로 자름 |

## 7. 품질 확인 방법

고정 질문을 정해 두고 바꾸기 전과 후에 실제 모델로 한 번씩 돌려 비교한다. 결과는 [AI-PLANNING.md](../../AI-PLANNING.md)에 기록한다.

| 지표 | 목표 |
| --- | --- |
| 실제 장소 비율(결과 장소 중 후보에서 나온 비율) | 100% |
| 일정 짜기 구성 준수(날마다 식사 2·카페 1·관광 최소, 보충 전) | 보충 전 80% 이상, 보충 후 100% |
| 범위·시간대 요청 준수 | 100% |
| 챗봇 why 포함 | 100% |
| 하루 동네 바뀜 횟수 | 바꾸기 전보다 적게 |

일정 짜기 질문: 강릉 2박3일 보통, 부산 당일 여유롭게, 전주 1박2일 알차게 + '맛집만 5곳', 속초 1박2일 + '저녁 이후 계획', 경주 1박2일 + 꼭 갈 곳 식당.
챗봇 질문: 강릉 1박2일 카페 투어, 부산 아이랑 비 오는 날, 전주 혼자 먹방, 여수 밤바다 코스, 대구 맛집만 3곳.

## 8. 오류와 경계

| 경우 | 처리 |
| --- | --- |
| 지역을 모름(챗봇) | 후보 없이 보낸다. 지역을 묻는다 |
| 검색 실패·결과 없음 | 후보 없이 지금 방식으로 동작 |
| 모르는 ref·ref 없는 항목 | 그 항목만 버린다 |
| 후보가 너무 적음(작은 군 지역) | 있는 만큼 보내고, 일정 짜기는 보충·알림으로 처리 |
| 요청 크기 | 일정 짜기 후보 120 × 약 90자 ≈ 1.1만 자, 챗봇 40곳. 서버 상한 안에서 검사한다 |
| 무료 검색 한도 | 일정 짜기 한 번에 최대 약 25번, 챗봇 4번. 카카오 하루 10만 건에 비해 적다 |

## 9. 테스트

- 단위: 후보 모으기(검색어 표, 중복·기존 장소 제외, 상한, 실패 시 빈 목록), ref 검사·버림, 후보 kind 적용, 보충 시 남은 후보 우선, 옛 응답 받기.
- 서버: 후보 요청 검사(개수·글자 수), 지시문에 후보 칸·규칙 순서·출력 전 확인이 들어가는지, 후보 없는 요청은 지금 지시문 그대로인지.
- e2e: 고정 응답이 ref로 답할 때 일정 짜기 결과와 챗봇 확인 카드(이유 한 줄)가 보이고 담기가 되는지.
- 실제 모델: 7절 비교(수동, 기록).

## 10. 범위에 넣지 않는 것

- 모델 교체, 구글 검색 근거, Function Calling.
- 후보의 평점·리뷰 수(카카오 검색 결과에 없다).
- 검색 결과의 서버 캐시. 호출 수가 문제가 되면 따로 정한다.
