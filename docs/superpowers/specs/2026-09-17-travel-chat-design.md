# 대화형 여행 탐색 챗봇 설계 (2026-09-17)

이 문서는 챗봇 기능의 설계 결정과 근거를 기록한다. 화면별 요구사항은 [기획안 35절](../../기획안-v0.1.md), 검증 가능한 요구사항은 [OpenSpec travel-planning 명세](../../../openspec/changes/plan-travel-companion-mvp/specs/travel-planning/spec.md)에 있다. 이 문서는 구현 완료를 뜻하지 않는다.

## 1. 목적과 문제

기존 AI 일정 만들기(`trips/ai`)는 지역을 고른 뒤 날짜·동행·취향을 단계로 받는다. 이 흐름은 **어디로 갈지 이미 정한 사용자**에게는 빠르지만, 첫 단계인 지역 선택에서 막히는 사용자를 돕지 못한다. "3일 쉬는데 어디 가지"라는 상태의 사용자는 첫 화면을 넘지 못한다.

챗봇은 이 진입 장벽을 낮추는 두 번째 경로다. 목적지를 정하지 못한 사용자가 대화로 후보를 좁히고, 그 결과를 일정으로 옮기는 데까지 한 흐름으로 잇는다.

부수 목적으로 이미 만든 일정을 대화로 고치는 경로도 함께 제공한다. 기획안 20절이 "3일차 카페 하나 빼고 숙소에 일찍 도착하게 바꿔줘" 같은 자연어 변경을 이미 규정하고 있으나, 그것을 받을 입력 수단이 앱에 없었다.

## 2. 기존 결정과의 관계

### 8절의 갱신

기획안 8절은 "선택형 단계로 받고 자유 텍스트 입력은 보조로 둔다"고 정했다. 이 결정을 다음과 같이 갱신한다.

> 조건이 정해진 사용자는 선택형 단계로 받는다. 조건이 정해지지 않은 사용자에게는 대화형 탐색을 제공한다. 대화형에서 얻은 결과도 일정 저장은 선택형 확인 카드를 거친다.

핵심은 **자유 텍스트는 탐색까지만 쓰고, 저장은 선택형을 유지한다**는 점이다. 20절의 "AI가 단독으로 반영하지 않는다"는 규칙은 그대로 살아 있다.

### 검증 원칙의 적용 위치 구분

AGENTS.md와 기획안 8절은 영업정보를 추측해 표시하지 말라고 정하고 있다. 이 규칙의 적용 위치를 다음과 같이 나눈다.

| 대상 | 규칙 |
| --- | --- |
| 일정에 저장되는 값 | 검증된 출처에서만 가져온다. 좌표·주소·분류는 카카오 장소 검색 결과를 쓴다. 모델이 만든 값을 저장하지 않는다 |
| 대화 중 안내 | 모델이 답할 수 있다. 확인된 사실과 시각적으로 구분하고 확인할 수 있는 링크를 함께 제공한다 |

영업시간은 일정 항목에 저장되지 않으므로 두 규칙이 충돌하지 않는다. 사용자가 "몇 시에 열어"를 물었을 때 아무 답도 못 하면 챗봇을 쓸 이유가 없다는 판단(2026-09-17 사용자 결정)에 따른 것이다.

## 3. 기반 기술

모델은 기존 일정 생성과 같은 **Gemini `gemini-3.5-flash-lite`**를 쓴다. 대화는 한 여행을 계획하는 동안 여러 번 호출되므로 무료 하루 500회 한도가 상위 모델의 품질 차이보다 중요하다. 모델 변경은 `GEMINI_MODEL` 비밀값으로 하며 앱 코드를 고치지 않는다.

호출 경로는 일정 생성과 같다.

```text
브라우저 → Supabase Edge Function(ai-chat) → Gemini
             로그인 확인 · 범위 검사 · 키 보관
```

`ai-plan`과 별개 함수로 둔다. 지시문·응답 형식·검증 규칙이 다르고, 한쪽 배포가 다른 쪽을 멈추게 하지 않아야 하기 때문이다.

### Function Calling을 쓰지 않는 이유

모델이 등록 함수를 직접 호출하게 하는 방식(Function Calling)은 쓰지 않는다. 이유는 두 가지다.

첫째, 이 앱은 모델이 낸 장소 이름을 카카오 장소 검색으로 대조한 뒤에만 확정한다. 모델의 호출이 곧 실행 지시가 되면 그 사이에 검증 단계를 넣기가 구조적으로 어색해진다.

둘째, 기획안 20절이 AI 단독 반영을 금지하고 있다. 사용자 확인을 반드시 거치게 할 것이라면 모델이 직접 실행할 이유가 없다.

대신 모델은 **구조화된 JSON 초안만 반환**하고, 등록은 사용자 확인 뒤에 앱 코드가 수행한다. 사용자가 보는 경험은 같고 안전성만 높아진다.

## 4. 화면 배치

진입점은 화면의 성격에 따라 다르게 둔다.

| 화면 | 진입 방식 | 열리는 형태 | 대화 대상 |
| --- | --- | --- | --- |
| 여행 목록 | 기존 `AI 일정 만들기` 버튼 → 방식 선택 화면 | 전체 화면 | 새 여행 |
| 여행 상세 | 오른쪽 아래 떠 있는 버튼 (신규) | 하단 시트 | 그 여행 |

### 여행 목록에 떠 있는 버튼을 두지 않는 이유

여행 목록 상단에는 이미 `AI 일정 만들기` 버튼이 있다. 여기에 챗봇 버튼을 따로 띄우면 한 화면에 AI 진입점이 둘이 되어, 사용자가 매번 둘의 차이를 판단해야 한다. 실제로는 같은 목적에 방식만 다르다.

그래서 진입점은 하나로 유지하고, 버튼을 누른 뒤 첫 화면에서 방식을 고르게 한다. 여행이 없을 때 쓰는 빈 상태 카드와 같은 형태를 쓴다.

```text
AI로 일정 만들기

┌──────────────────┐  ┌──────────────────┐
│ 조건 고르기       │  │ 대화로 찾기       │
│ 지역·날짜·동행을  │  │ 어디 갈지 정하지  │
│ 골라 만들기       │  │ 못했다면          │
└──────────────────┘  └──────────────────┘
```

### 여행 상세에 떠 있는 버튼을 두는 이유

이 화면의 하단 전폭 바는 `일정 추가`가 이미 쓰고 있다. 전폭 바를 하나 더 둘 자리가 없고, 기존 바에 버튼을 끼우면 360px에서 줄바꿈된다.

오른쪽 아래 구석은 앱 전체에서 쓰이지 않는다. 여기에 두면 기존 동작과 다른 종류라는 신호가 자연스럽게 전달된다.

배치 값은 다음과 같다.

- 크기 56px, 오른쪽 여백 16px
- 기존 동작 바 위로 12px. 동작 바가 안전 영역을 이미 처리하므로 그 위에 얹는다
- `z-index: 10004`. 동작 바(10002)와 상단 바(10006) 사이다
- 목록 마지막 항목을 가리지 않도록 본문 하단 여백을 확보한다

오류 알림이 같은 자리에 뜨므로 `--toast-bottom-offset` 변수를 올려 알림을 위로 민다. 이 변수는 `theme.css`에 선언만 되어 있고 아직 쓰이지 않는다.

### 하단 시트를 쓰는 이유

여행 상세에서 챗봇을 여는 목적은 그 일정을 고치는 것이므로, 고치는 대상이 보여야 한다. 전체 화면으로 덮으면 변경 내용을 확인하러 매번 닫아야 한다.

시트는 처음에 화면 절반쯤 올라오고 위로 끌면 전체가 된다. 변경 카드가 뜨면 뒤의 일정에서 해당 항목을 강조해, 시트를 닫지 않고도 무엇이 바뀌는지 볼 수 있다.

`theme.css`의 `menu-sheet` 패턴과 `sheet-rise` 애니메이션, `appDismissible` 지시자를 그대로 쓴다. 새 팝오버를 만들 때 `theme.css`의 `body:has(...)` 선택자 목록에 추가하라는 기존 주석 규약을 따른다.

## 5. 대화 흐름

```text
빈 화면 + 추천 질문 칩
   │
   ├─ 칩을 누르거나 직접 입력
   ▼
Edge Function(ai-chat) → 범위 검사
   │
   ├─ 범위 밖 ────────→ 정해진 안내 + 칩 다시 표시 (상태 변화 없음)
   ├─ 탐색 답변 ──────→ 지역·테마 제안 + 이어지는 칩
   ├─ 참고 정보 ──────→ AI 답변 표시 + 확인 링크
   └─ 일정 초안 ──────→ 카카오 대조 → 확인 카드
                          │
                          ├─ [담기] → 새 여행 생성 또는 기존 여행에 추가
                          └─ [그대로] → 초안 폐기
                                │
                          담긴 뒤 [되돌리기] 제공
```

## 6. 기능별 설계

### 추천 질문 칩

빈 화면 대신 칩을 4~6개 보여준다. 어디서 열었는지에 따라 내용이 다르다.

| 여는 위치 | 칩 예시 |
| --- | --- |
| 여행 목록 | 이번 주말 근교 · 혼자 가기 좋은 소도시 · 아이와 갈 만한 곳 · 아무 데나 뽑기 |
| 여행 상세 | 순서 정리하기 · 카페 추가 · 이 날 너무 빡빡해 · 근처 맛집 |

여행 상세의 칩은 그 여행의 상태를 반영한다. 미배치 항목이 있으면 "남은 장소 배치하기"를 넣는 식이다.

### 랜덤 여행지 뽑기

모델에게 자유 생성을 맡기지 않는다. 지역 목록에서 앱이 먼저 뽑고, 모델에게는 **그 지역을 왜 갈 만한지 설명하는 일만** 맡긴다. 존재하지 않는 지역이 나오는 사고를 구조적으로 막는다.

같은 지역이 연달아 나오지 않도록 최근에 뽑은 값은 잠시 제외한다.

### 국내 여행 한정 범위 제한

지시문만으로 막지 않고 Edge Function에서 응답을 함께 검사한다. 질문 종류별 처리는 다음과 같다.

| 종류 | 예시 | 처리 |
| --- | --- | --- |
| 일정 탐색·수정 | 3일 쉬는데 어디 가지 / 3일차 하나 빼줘 | 정상 처리 |
| 참고 정보 | 몇 시에 열어 / 입장료 얼마야 | AI가 답하되 구분 표시 + 확인 링크 |
| 주관적 평가 | 속초 재밌어 / 여기 맛집 뭐야 | 장소 추천으로 바꿔 답한다. "맛있다"는 단정하지 않고 어떤 곳이 있는지 설명한다 |
| 앱 범위 밖 | 항공권 얼마야 / 렌터카 예약 | 다루지 않음을 알리고 일정으로 유도한다. 거절 문구로 끝내지 않는다 |
| 여행 무관 | 코드 짜줘 / 주가 알려줘 | 정해진 안내를 돌려주고 칩을 다시 보여준다 |

### 참고 정보의 표시

영업시간·휴무·요금·예약 여부는 AI가 답하되 확인된 사실과 구분한다.

```text
불국사

  🤖 AI 답변 · 부정확할 수 있습니다
  ┌────────────────────────────────┐
  │ 보통 오전 7시부터 오후 6시까지  │
  │ 운영합니다.                     │
  └────────────────────────────────┘

  정확한 정보는 여기서 확인하세요
  [네이버 지도]  [카카오맵]
```

링크는 두 곳을 함께 준다. 네이버는 국내 장소의 영업정보가 더 잘 채워져 있고, 카카오는 검색에서 얻은 장소 ID로 정확한 상세 페이지를 열 수 있다. 네이버는 장소 ID가 없으므로 이름으로 검색하는 주소를 만든다.

이 표시 규칙은 챗봇만의 것이 아니라 앱 공통으로 둔다.

### 확인 카드

AI가 말로 "버튼을 눌러 주세요"라고 안내하지 않는다. 말풍선 안에 실제 버튼이 있는 카드를 띄운다. 바뀌기 전과 후를 나란히 보여준다.

```text
┌─ 1일차 순서를 바꿉니다 ───────────┐
│  현재            바꾼 뒤           │
│  1 철뚝소머리집   1 복사꽃마을     │
│  2 복사꽃마을     2 한과마을       │
│  3 한과마을       3 철뚝소머리집   │
│                                   │
│  이동 거리가 12km 줄어듭니다       │
│                                   │
│  [ 바꾸기 ]      [ 그대로 두기 ]   │
└───────────────────────────────────┘
```

내부 처리를 그대로 노출하지 않는다. 순서 교환을 "A ↔ B 추가 완료"처럼 적지 않는다.

담은 뒤에는 되돌리기를 제공한다. 기획안 20절의 공통 초안 규칙을 따른다.

### 허용하는 변경

| 변경 | 쓰는 함수 |
| --- | --- |
| 장소 추가 | `appendStop` |
| 장소 삭제 | `removeStop` |
| 순서 변경 | `moveStop` |
| 날짜 이동 | `placeStopOnDate` |

거리 계산은 앱이 직접 한다. 좌표가 이미 저장되어 있으므로 모델의 추측이 들어갈 자리가 없다. 모델은 "순서를 바꿔 달라"는 의도만 해석한다.

## 7. 대화 품질 규칙

다른 앱을 살펴본 결과 반복해서 나타나는 문제가 있었다. 같은 문제를 만들지 않기 위한 규칙이다.

- **묻지 않은 일을 하지 않는다.** 사용자가 "추가해줘"라고 하면 추가만 한다. 순서 정렬을 덤으로 하지 않는다.
- **의도가 애매하면 먼저 묻는다.** 짐작으로 일을 벌이면 사용자가 원복해야 한다. 한 줄로 되묻는다.
- **같은 내용을 반복하지 않는다.** 이미 보여준 목록을 답변마다 다시 적지 않는다.
- **꾸밈말을 줄인다.** 이모지는 상태 표시에만 쓰고 문장 끝 장식으로 쓰지 않는다.

## 8. 상태와 제한

상태는 기존 `AiPlanStore`와 같은 NgRx signalState 패턴으로 별도 store에 둔다. 보관하는 값은 대화 기록, 진행 중 요청의 `AbortController`, 초안별 선택 집합, 마지막 적용 결과다.

대화 기록은 기기에만 저장하고 서버로 보내지 않는다. 사진·여행 기록 기본 비공개 원칙과 같은 기준이다.

**대화 한 세션의 호출 상한은 20회다.** 무료 하루 500회를 앱 전체가 나눠 쓰므로 한 사람이 몰아 쓰면 나머지가 못 쓴다. 상한에 이르면 지금까지의 초안을 담고 새 대화를 시작하도록 안내한다. 기획안 8절의 일별 호출 제한 규칙을 세션 단위로 구체화한 것이다.

## 9. 검증 기준

- 목록에서 열기: 방식 선택 → 대화 → 초안 → 담기 → 새 여행 생성 → 여행 상세 도착
- 상세에서 열기: 떠 있는 버튼 → 시트 → 수정 요청 → 확인 카드 → 적용 → 되돌리기
- 범위 검사: 여행 무관 질문에 정해진 안내가 나오고 대화 상태가 바뀌지 않는다
- 참고 정보: AI 답변이 구분 표시와 함께 나오고 두 링크가 모두 동작한다
- 실패 처리: 연결 실패·시간 초과·한도 초과·빈 결과를 구분해 알리고 대화 기록을 보존한다
- 호출 상한: 20회에 이르면 안내가 나오고 초안을 담을 수 있다
- 화면: 360px에서 떠 있는 버튼이 마지막 항목을 가리지 않는다. 시트가 열린 동안 뒤 배경이 스크롤되지 않는다. 키보드로 조작할 수 있다

## 10. 구현 순서

2026-09-17 사용자 결정으로 화면과 서버를 나눠 진행한다.

| 단계 | 내용 | DB |
| --- | --- | --- |
| 13-A | 시트·칩·확인 카드·대화 화면. 고정 응답으로 흐름 검증 | 필요 없음 |
| 4절 | Supabase 여행 저장·RLS | 이 단계가 DB 연결 |
| 13-B | `ai-chat` 함수, 서버측 호출 제한, 대화 저장 | 4절 위에 얹는다 |
| 8절 | 친구 초대·공유 서버 권한 | 4절 위에 얹는다 |

화면을 먼저 만드는 이유는 시트 높이·확인 카드 가독성·칩 개수처럼 그려 봐야 아는 것들이 남아 있고, 서버를 다 만든 뒤 배치를 고치면 되돌리는 비용이 크기 때문이다. 12절의 친구 초대·가계부도 같은 방식으로 진행했다.

대화 저장은 `TripRepository`처럼 인터페이스 뒤에 두어 13-B에서 구현만 갈아 끼운다. 화면 코드는 그때 고치지 않는다.

**호출 제한은 13-B로 미룬다.** 세션당 20회를 브라우저에서 세면 개발자 도구로 지울 수 있다. 실제로 막으려면 누가 몇 번 썼는지 서버가 알아야 한다. 혼자 또는 친구 몇 명이 쓰는 동안은 문제가 되지 않으므로 화면 단계에서는 안내만 구현한다.

## 11. 이번 범위에 넣지 않는 것

- **TourAPI 휴무일 연동.** 관광공사 API의 `restdate` 필드로 박물관·미술관의 실제 휴관일을 표시할 수 있다. 카페·식당은 대상이 아니다. 별도 연동 작업이므로 후속으로 둔다.
- **네이버 지도 상세정보 직접 조회.** 네이버 지역 검색 API는 영업시간을 주지 않고, 페이지를 긁어오는 것은 약관과 AGENTS.md 양쪽이 금지한다.
- **경로 소요시간 안내.** 경로 API 연동 뒤에 가능하다. 그전에는 확인이 필요하다고 표시한다.
- **날씨 안내.** 기상 API를 붙이지 않았다.
- **대화 기록 서버 저장과 기기 간 이어보기.** Supabase 여행 저장이 끝난 뒤 검토한다.
