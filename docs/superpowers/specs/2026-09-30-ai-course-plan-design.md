# AI 일정 짜기: 시간순 코스와 세부 분류 설계

- 작성일: 2026-09-30
- 브랜치: `feat/ai-plan-costs`
- 상태: 설계 문서 승인됨(2026-09-30, 일차 이동 유지·분류 통일 반영). 구현 전.
- 선행 작업: [예산·요금 기준·체류시간](../../ai-plan-estimates.md), [OpenSpec add-ai-plan-estimates](../../../openspec/changes/add-ai-plan-estimates/proposal.md)

## 1. 배경과 목표

현재 일정 짜기는 하루 장소 5·식사 3·카페 2곳의 후보 목록을 받아 골라 담는다. 사용자가 보여준 참고 화면(다른 서비스의 코스 결과)과 비교해 다음이 부족하다.

1. 분류가 장소·식사·카페 세 가지라 관광·액티비티·쇼핑·숙소가 구분되지 않고, 숙소는 아예 추천하지 않는다.
2. 결과가 후보 목록이라 하루를 어떤 순서·시각으로 다니는지 보이지 않는다.
3. 예상 비용·체류시간 기능은 앱에만 반영되고 서버 함수가 배포되지 않아 모두 "미정"으로 표시된다(2026-09-30 운영 함수 직접 호출로 확인: 20곳 모두 `estimate` 없음).

목표는 **시간순 코스**를 보여 주고 사용자가 원치 않는 항목을 **해제만** 해서 담게 하는 것이다. 장소마다 **요금과 요금 기준**을 보여 준다.

### 사용자 결정 (2026-09-30)

- 분류: 장소 → 관광·액티비티로 나누고 쇼핑·숙소를 추가한다.
- 결과: 시간순 코스. 대안 제시나 추가 후보 없이 해제만 가능하다.
- 요금: 참고 화면처럼 요금 기준을 보여 준다. 검색 연동(Google 검색 근거)은 하지 않는다.
- 예산 구성은 구현자가 정한다(4절).

### 하지 않는 것

- 검색 연동으로 실제 요금을 조회하거나 출처 링크를 붙이는 일.
- 출발지에서 오는 교통비 계산(출발지 입력과 요금 출처가 없다).
- 실제 경로 조회. 이동시간은 모델 추정만 표시한다.
- 해제·일차 이동 후 시각 재배치, 대안 장소 교체.

## 2. 규칙상 제약

AGENTS.md: 일정에 **저장하는** 좌표·주소·분류·경로시간은 검증된 출처에서만 가져온다. 추측을 확인된 사실처럼 표시하지 않는다.

- 좌표·주소는 지금처럼 장소 검색 결과에서만 가져온다. 분류는 검색 분류가 모델 분류보다 우선한다(3.3).
- 추천 시각과 이동시간은 모델 추정이다. **화면에만 표시**하고 `fixedTime`이나 경로시간으로 저장하지 않는다. 메모에 "AI 추천 시각"으로 남긴다.
- 요금은 모두 "AI 추정"으로 표시한다. 참고 화면의 "공식 홈페이지 기준" 같은 표현은 쓰지 않고, 계산 기준(상품·수량)만 보여 준다.
- 직선거리는 확인된 두 좌표로 계산한 사실값이므로 표시할 수 있다.

## 3. 설계

### 3.1 분류와 데이터 모델

| 화면 라벨 | 저장값 | 비고 |
|---|---|---|
| 관광 | `place` | 기존 값의 라벨만 바꾼다. 이미 저장된 일정은 그대로 관광이 된다. |
| 액티비티 | `activity` | 신규 |
| 식사 | `meal` | 기존 |
| 카페 | `break` | 기존(라벨만 카페) |
| 쇼핑 | `shopping` | 신규 |
| 여유시간 | `buffer` | 기존, AI는 만들지 않는다 |
| 숙소 | `stays` 항목 | 일반 장소가 아니라 기존 숙박 모델로 담는다 |

- **분류 체계는 앱 전체에서 하나로 통일한다(2026-09-30 사용자 결정).** 일정 짜기, 여행 상세, 장소 추가·수정, 구름이 챗봇(명령 대상·응답), 통계, 가계부 연결, 공동 편집 미리보기가 같은 여섯 분류와 같은 라벨·색·아이콘을 쓴다. 숙소도 여행 상세에서 같은 "숙소" 라벨·색을 쓴다. 정의는 `trips/model/trip.ts`(라벨)와 `trips/util/kind-tone.ts`(색·아이콘)에만 두고, 다른 기능은 자체 라벨 표를 두지 않고 이것을 가져다 쓴다. 서버 프롬프트의 분류 문자열(관광·액티비티·식사·카페·쇼핑·숙소)도 같은 라벨을 쓴다.
- `StopKind`에 `activity`·`shopping`을 추가한다. `Record<StopKind, …>`를 쓰는 라벨·색·아이콘·기본 이름 표는 컴파일 오류로 누락을 잡는다. 영향 파일: `trips/model/trip.ts`, `trips/util/kind-tone.ts`, `trips/util/factories.ts`, `trips/feature/stop-form`, `trips/feature/trip-detail`, `travel-chat`(명령 대상·모델), `stats/model/visit-stats.ts`, `expenses/util/expense-link.ts`, `collaboration/util/preview-trip.ts`, `ai-planning` 전반.
- DB: `stop_kind` 열거형에 값을 **추가만** 하는 마이그레이션 `alter type public.stop_kind add value 'activity'; … 'shopping';`. 기존 행은 바뀌지 않는다. 개발·운영이 같은 Supabase를 쓰므로 적용 즉시 운영에 반영된다. 새 값을 저장하는 프론트엔드보다 먼저 적용해야 한다(6절).
- 이전 클라이언트(v0.9.10)가 새 값을 읽으면 라벨이 비어 보일 수 있다. 읽는 쪽에서 모르는 값은 관광으로 표시하도록 방어한다.

### 3.2 서버 요청·응답 (`supabase/functions/ai-plan`)

검색 없이 한 번만 호출하는 구조는 유지한다. 인증·한도·오류 코드도 그대로다.

응답 항목 스키마(추가·변경 부분):

```json
{
  "day": 1,
  "order": 1,
  "name": "해운대 블루라인파크 해변열차",
  "kind": "액티비티",
  "start": "11:25",
  "estimate": {
    "cost": { "min": 12000, "max": 12000, "basis": "person", "quantity": 1, "assumption": "성인 1인 해변열차 2회 탑승권" },
    "stay": { "min": 60, "max": 70, "reason": "해변열차 왕복과 사진 촬영" }
  },
  "moveToNext": { "mode": "도보", "minutes": 10 }
}
```

- `kind` 열거형: 관광·액티비티·식사·카페·쇼핑·숙소.
- `order`: 그날 안의 방문 순서(1부터). `start`: 추천 시작 시각 `HH:mm`.
- `moveToNext`: 다음 항목까지의 이동. 수단은 도보·대중교통·자가용·택시 중 하나. 마지막 항목과 숙소는 `null`.
- 숙소는 그날 마지막 항목으로 두고, 마지막 날에는 넣지 않는다. 숙소의 `estimate.cost`는 `room_night` 기준이다.
- 프롬프트 기본 구성: 하루 관광 2~3, 액티비티 또는 쇼핑 1, 식사 2(점심·저녁), 카페 1, 숙소 1(마지막 날 제외). 사용자의 추가 요청이 종류·개수를 정하면 기존 `noteSetsScope` 규칙대로 기본 구성을 빼고 요청을 따른다.
- 일정 밀도(여유롭게·보통·알차게)에 따라 하루 첫 시각과 항목 수를 조절하도록 지시한다. 이동수단 조건을 `moveToNext.mode`에 반영하도록 지시한다.
- 요금 지시는 기존 규칙을 유지한다: "공식·확인됨·최신" 표현과 출처 URL을 만들지 않고, 추정이 어려우면 `null`.

### 3.3 앱의 응답 해석과 검증 (`ai-planning/util/ai-response.ts`, `verify-places.ts`)

- `start`는 `HH:mm` 형식과 00:00~23:59 범위를 검사하고, 틀리면 `null`(시각 미정)로 둔다.
- `order`가 없거나 겹치면 응답 순서를 쓴다. 같은 날 안에서 `start`가 앞 항목보다 이르면 그 항목의 시각만 미정으로 낮춘다(순서는 믿고 시각은 버린다).
- `moveToNext.minutes`는 1~600 정수만 받고, 수단은 허용 목록만 받는다. 아니면 이동 정보 미정.
- 분류: 장소 검색 분류가 음식점·카페·숙박이면 그 분류를 쓰고, 그 밖의 분류에서는 모델이 준 관광·액티비티·쇼핑을 유지한다(검색 분류로 셋을 구분할 수 없기 때문). 검색 분류가 숙박인데 모델이 숙소가 아니라고 했거나 그 반대면 검색 분류를 따른다.
- 이전 응답(`start`·`order`·`moveToNext` 없음)도 받아서, 시각 없이 순서대로 표시한다.
- 실존이 확인되지 않은 장소는 지금처럼 결과에서 뺀다. 뺀 뒤 앞뒤 항목 사이의 모델 이동시간은 더 이상 맞지 않으므로 표시하지 않고 직선거리만 보여 준다.

### 3.4 결과 화면 (`ai-plan-flow`)

- 상단: 예산 요약(4절).
- 일차별 섹션 "1일차"·"2일차" 아래에 **추천 시각순 카드**를 둔다.
  - 1행: `11:25 (1시간 10분) · 액티비티 · 해운대구`. 시각이 미정이면 시각을 빼고, 체류가 미정이면 괄호를 뺀다. 지역은 확인된 주소의 시·군·구.
  - 2행: 장소명과 실존 확인 표시.
  - 오른쪽: 요금 `12,000원` 또는 `약 12,000~15,000원`, 미정이면 `요금 미정`. 모든 요금 옆에 "AI 추정"을 붙인다.
  - 3행: `요금 기준: 1인당 12,000원 × 2명 × 1회 · 성인 1인 해변열차 2회 탑승권`(기존 `costBasis` 형식).
  - 지도 링크(기존 UiMapLinks), 체크박스(해제).
- 카드 사이: `↓ 도보 약 10분 · AI 추정 · 직선 0.8km`. 모델 이동 정보가 없거나 무효면 직선거리만, 좌표가 없으면 생략한다.
- 해제한 카드는 흐리게 남기고 합계에서 뺀다. 다른 카드의 시각은 그대로 둔다. 해제한 카드를 건너뛴 앞뒤 카드 사이에는 직선거리만 다시 계산해 표시한다.
- 기존 일차 변경 선택(`setDay`)은 유지한다(2026-09-30 사용자 결정). 다른 일차로 옮긴 항목은 그날 코스의 맨 끝에 붙고 추천 시각은 미정으로 표시한다. 옮긴 항목과 원래 앞뒤 항목의 모델 이동 정보는 지우고 직선거리만 표시한다. 담을 때 메모에도 추천 시각을 남기지 않는다. 숙소는 그날 마지막 자리를 유지하도록 옮긴 항목을 숙소 앞에 둔다. 숙소를 다른 일차로 옮기면 체크인 날짜가 그 일차가 된다.
- 날짜 미정 여행이면 숙소 카드는 표시하되 담기에서 제외하고 "날짜를 정하면 숙소를 담을 수 있어요"라고 안내한다. 숙박 모델은 체크인 날짜가 필요하기 때문이다.
- 디자인은 `docs/design/DESIGN.md`의 토큰·공통 UI와 `.impeccable/surfaces/`의 화면 계약을 따른다. 참고 화면은 구조만 참고하고 시각 요소를 복제하지 않는다.

### 3.5 담기 (`trips/util/ai-selection.ts`)

- 숙소가 아닌 항목: 지금처럼 `createStop`으로 해당 날짜에 **코스 순서대로** 추가한다. `kind`는 3.1 표의 저장값, `stayMinutes`는 체류 상한, `estimatedCost`는 요금 상한.
- 숙소 항목: `createStay`로 체크인 = 그 일차 날짜, 체크아웃 = 다음 날, `estimatedCost` = 요금 상한, 예약 상태 `unknown`. 같은 숙소가 연속 일차에 나오면 하나로 합쳐 체크아웃을 늘린다.
- 메모: 기존 `estimateMemo`에 `AI 추천 시각 11:25`를 한 줄 추가한다. 이동시간은 메모에도 남기지 않는다(경로시간 저장 금지 규칙에 가깝고, 담은 뒤 순서가 바뀌면 틀린 값이 된다).
- 해제한 항목은 담지 않는다.

## 4. 예산

- 상단 요약: **예상 총액**(선택 항목 요금 범위 합), 입력 예산이 있으면 **여유 n원** 또는 **초과 n원**.
- 항목별 합계: 숙박(숙소) · 식비(식사+카페) · 관광·체험(관광+액티비티) · 쇼핑(선택 지출).
- 쇼핑은 개인차가 커서 총액에는 포함하되 "선택 지출"로 표시한다. 쇼핑 요금이 미정이면 미정 개수로만 센다.
- 안내 문구: "출발지 교통비와 이동 교통비는 포함하지 않아요. 요금은 AI 추정이며 미정 항목은 합계에서 빠져요."
- 예산 초과 판단은 기존처럼 총액 상한 기준이고, 예산 안에 든다고 보장하지 않는다.
- 기존 `summarizeEstimates`를 분류별 합계를 함께 돌려주도록 넓힌다.

## 5. 오류 처리

- 서버·모델 오류, 한도 초과, 빈 응답: 기존 처리(조건 화면으로 돌아가 메시지 표시)를 유지한다.
- 항목 단위의 잘못된 값(시각·이동·요금·체류)은 그 값만 미정으로 낮추고 항목은 유지한다.
- 모르는 분류 문자열은 관광으로 둔다.
- 확인된 장소가 하나도 없으면 기존 "실제로 있는 장소를 찾지 못했어요" 메시지를 쓴다.

## 6. 검증과 배포

### 단위 테스트
- `ai-response`: 새 필드 해석, 잘못된 시각·순서·이동, 이전 응답 호환, 숙소·액티비티·쇼핑 분류.
- `verify-places`: 검색 분류와 모델 분류 결합 규칙.
- `plan-estimate`: 분류별 합계, 쇼핑 선택 지출, 숙소 `room_night`.
- `ai-selection`: 숙소 → `stays`, 연속 숙박 병합, 코스 순서 유지, 메모의 추천 시각, 날짜 미정 시 숙소 제외.
- `ai-plan-store`: 해제 후 합계, 해제 카드 건너뛴 직선거리, 일차 이동 시 맨 끝(숙소 앞) 배치와 시각·이동 정보 해제.
- 분류 통일: 기능별로 남아 있던 자체 분류 라벨 표가 없고 모두 공통 정의를 쓰는지 확인한다.
- 서버 `handler`·`prompt`: 새 스키마와 기본 구성 문구, `noteSetsScope` 동작 유지.

### e2e (픽스처, 데스크톱·360px)
- 시간순 카드와 이동 정보 표시, 해제 후 합계·직선거리, 담은 뒤 여행 상세의 분류·숙소·메모 확인, 저장 후 새로고침.

### 실제 확인
- 함수 배포 뒤 실제 생성 1회: 분류 분포, 시각 순서, 요금·요금 기준 채움 비율, 생성 시간.

### 배포 순서 (각 단계 직전에 사용자 확인)
1. DB 마이그레이션(`stop_kind` 값 추가).
2. `ai-plan` 함수. 이전 클라이언트는 새 필드를 무시하고 순서대로 표시하므로 먼저 배포해도 된다. 다만 이전 클라이언트는 `kind` "액티비티"·"쇼핑"·"숙소"를 모르는 라벨로 보고 장소로 담는다.
3. 프론트엔드.
