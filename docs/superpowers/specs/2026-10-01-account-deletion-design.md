# 회원탈퇴 마무리 설계

2026-10-01 작성. 사용자 요청: 회원탈퇴 기능을 만든다. 기존 정책은 [기획안](../../기획안-v0.1.md) 409~414줄, 요구사항은 OpenSpec `plan-travel-companion-mvp` 4.3b와 travel-planning 명세 "Delete own account"에 있다.

## 1. 지금 상태 (2026-10-01 조사)

| 항목 | 상태 |
| --- | --- |
| 화면 | 내 정보의 빨간 "회원탈퇴" → '탈퇴' 입력 → "계정 영구 삭제". 설정이 꺼져 있어 지금은 "준비 중"만 보인다 |
| 서버 함수 `delete-account` | 코드 있음. 토큰으로 본인을 확인하고 그 계정만 지운다(요청의 사용자 ID는 무시). 운영 배포 기록 없음 |
| 함께 지워지는 데이터 | 내 여행 전체(일정·숙소·가계부·지출·정산·멤버·초대), 다른 여행의 내 멤버 자격, AI 사용량, 역할, 공지 읽음, 문의·답변 |
| 남는 데이터 | 다른 사람 여행에 내가 남긴 지출(작성자만 비워짐), 그 가계부의 사람 이름, 기기에 저장된 대화·기록 |
| 테스트 | 함수 단위 테스트, 서버를 흉내 낸 e2e. 실제 탈퇴·삭제 연쇄의 SQL 검증 없음 |

## 2. 결정: 함께 쓰는 여행의 주인이 탈퇴하면 다른 멤버에게 넘긴다 (2026-10-01 사용자 결정, A안)

지금은 주인이 탈퇴하면 **여행이 통째로 지워진다.** 함께 편집하던 친구의 일정과 지출도 함께 사라진다. 앱 안에서는 주인이 '나가기'를 할 수 없게 막아 두었는데, 탈퇴는 이 막음을 거치지 않는다.

| 안 | 동작 | 장단점 |
| --- | --- | --- |
| **A. 가장 오래 함께한 멤버에게 넘긴다 (추천)** | 탈퇴 직전에 서버가 주인을 그 멤버로 바꾼다. 멤버가 없는 여행만 지운다 | 친구의 기록이 남는다. 받은 사람에게 알림(알림 기능이 있으면) |
| B. 모두 지운다 | 지금 동작. 탈퇴 확인 화면에 "함께 쓰는 여행 N개도 다른 사람에게서 지워져요"를 보인다 | 단순하지만 친구가 기록을 잃는다 |
| C. 넘기기 전까지 탈퇴를 막는다 | 함께 쓰는 여행이 있으면 "먼저 주인을 넘겨 주세요" | 확실하지만 주인 넘기기 화면이 따로 필요하다 |

## 3. 바꾸는 것 (A안 기준)

1. **서버 함수 `prepare_account_deletion()`**(본인만): 내가 주인인 여행 중 멤버가 있는 것은 가장 먼저 참여한 멤버를 주인으로 바꾸고, 그 멤버 행을 지운다. `delete-account`가 계정을 지우기 전에 부른다.
2. **확인 화면 문구**: 지워지는 것(내 여행·가계부·문의), 넘어가는 것(함께 쓰는 여행 N개 → 다른 멤버가 주인), 남는 것(다른 여행에 남긴 지출, Google·카카오 계정, 이 기기의 기록)을 세 줄로 보인다. 개수는 서버에서 읽는다.
3. **기기 정리**: 탈퇴가 끝나면 이 계정의 기기 저장(대화 기록·안내 본 기록·임시 값)을 지운다. 다른 계정의 기기 저장은 건드리지 않는다.
4. **배포와 켜기**: `delete-account` 함수를 배포하고, 배포 환경 변수 `SUPABASE_DELETION_ENABLED=true`로 화면을 연다. 개인정보 처리방침의 "회원탈퇴는 준비 중" 문구를 실제 절차로 바꾼다.
5. **검증**:
   - 로컬 SQL: 탈퇴 시 지워지는 표·남는 표·주인 넘기기를 확인한다(`supabase/tests/account-deletion.local.sql`).
   - e2e: 넘어갈 여행 개수 안내, 기기 정리.
   - 실제 계정: 별도 테스트 계정 두 개로 함께 쓰는 여행을 만든 뒤 주인 계정을 탈퇴하고, 다른 계정에 여행이 남는지 본다. 운영 DB를 개발과 함께 쓰고 있으므로 **테스트 계정만** 쓴다.

## 4. 범위에 넣지 않는 것

- 탈퇴 유예 기간(7일 뒤 삭제)과 복구.
- 사진 저장소 정리(아직 사진을 서버에 저장하지 않는다. 사진 저장을 만들 때 함께 정한다).
- 주인 넘기기 화면(C안을 고르지 않으면 필요 없다).
