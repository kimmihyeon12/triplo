# 국내 여행 비서 기획안 v0.1
작성일: 2026-09-09 · 상태: 검토용 초안 · 앱 구현 전
서비스명은 미정이다. 기존 콩·씨앗·새싹 콘셉트는 제외하고, 여행 경험치를 쌓으며 성장하는 독립적인 캐릭터를 사용한다. 작업 폴더명 travel-companion은 임시 기술 식별자로 유지한다.

## 1. 한 문장으로
AI가 제안한 장소 중 마음에 드는 곳만 골라 현실적인 여행 일정을 만들고, 다녀온 사진과 추억으로 나만의 지도와 작은 여행 친구를 키우는 국내 여행 비서.

핵심 반복 흐름: 발견 → 골라 담기 → 일정 정리 → 실제 여행 → 사진 기록 → 지도와 캐릭터 성장 → 다음 여행.
제품 우선순위: 사용자가 여행 전체를 이해하고 원하는 부분만 안전하게 고치는 일정 도구를 먼저 완성한다. 첫 경험의 중심은 여행 생성 → 장소·숙소 배치 → 전체 확인 → 부분 수정 → 여행 중 사용이다. 기록과 캐릭터는 이 흐름을 완료한 뒤 다시 찾을 이유를 만든다. 구체적인 사용 규칙과 단계별 통과 기준은 19~23절을 따른다.
북극성 지표 제안: 실제 여행을 완료하고 사진 또는 메모를 남긴 여행 수. AI 답변 생성 수는 보조 지표다.

## 2. 확정된 요청과 기획 가정
확정된 요청: 국내 여행, 반응형 웹/앱, AI 추천에서 선택 저장, 직접 장소 검색·저장, 당일 및 여러 박 여행, 숙소 등록, 차량/도보, 순서 변경·경로 정리, 장소 정보, 네이버/카카오 길찾기 연결, 주변·랜덤 탐색, 장소 사진 지도, 일정별 완료, 경험치·캐릭터.
확정 운영 방향: 초기 사용자는 본인과 친구들이며 비용 최소화를 우선한다. DB는 Supabase PostgreSQL로 선택하고 무료 플랜부터 시작한다. 일반 공개 시점과 유료 전환은 미정이다.
기획 가정: 한국어 우선, 1인·커플·친구의 자유여행, 웹/PWA 먼저. 친구들이 각자 사용하는 것과 같은 여행을 공동 편집하는 것은 구분한다.
추천 초기 범위: 장소 저장·기록은 국내 전역, AI 코스 품질 검증은 서울부터. 여행 시작일·종료일로 당일 및 여러 박의 일정을 지원한다. AI 품질은 하루 8개 이하 방문지로 검증하되 여행 기간을 1~3일로 제한하지 않는다.
장소/경로/AI 키, 서비스 계정, 과금 동의는 아직 없으며 실제 API 호출 품질은 미검증이다.

## 4. 대표 사용 시나리오
1. “서울에서 토요일 하루, 친구랑 카페랑 전시 위주로, 걷는 건 너무 많지 않게 짜줘.”
2. AI는 지역·날짜·동행·취향·이동 방식·출발지를 구조화한다. 날짜/출발지가 빠져 있으면 부담 없는 선택 칩으로 보완하고, 임시 가정은 보이게 한다.
3. 검증된 장소 후보 8~12개와 추천 흐름을 카드+지도에 제안한다. 사진, 추천 이유, 예상 체류, 확인된 운영정보를 보여준다.
4. 추천 결과의 검증된 방문 항목은 처음에 전체 선택되어 있다. 사용자는 원치 않는 장소를 해제하거나 “비슷한 곳으로 교체”하고 [선택한 장소 N개 일정에 담기]를 누른다. 전체 선택 상태만으로 확정 일정에 저장하지 않는다. 상세 선택·재추천 규칙은 25절을 따른다.
5. 선택한 장소를 여행 바구니에 담는다. 언제 갈지 정하지 않은 장소는 개인 장소함에 남길 수 있다.
6. 날짜별로 배치하고 [이동 줄이기]를 누른다. 출발·종료 지점, 예약 시각, 순서 고정 장소는 유지한다. 변경 전후 시간과 바뀐 순서를 확인하고 적용/되돌리기 한다.
7. 여행 당일 [다음 장소로]에서 네이버지도 또는 카카오맵을 연다.
8. 다녀온 장소에 완료 표시와 사진/짧은 메모를 남긴다. 지도에 사진 핀이 생기고 여행 친구가 성장한다.
9. 여행 완료 후 실제 방문한 장소와 기록을 여행별로 확인한다. 엽서형 요약과 미방문 지역 개인화 추천은 후속 단계로 둔다.

AI 실패·이용량 초과 시에도 수동 검색, 기존 일정 보기, 완료 표시, 사진 기록은 계속 사용할 수 있어야 한다.

여러 박 여행 예시: 4박 5일 여행을 만들고 A 숙소 2박과 B 숙소 2박을 등록한다. 다섯 날짜에 방문지를 나누어 배치하고, 숙소를 옮기는 날에는 A 체크아웃 → 방문지 → B 체크인을 확인한다. 숙소를 아직 정하지 않은 날짜는 미정으로 남겨두고 나중에 등록한다. 숙소 등록 상세는 16절을 따른다.

## 6. 차별화할 세 가지 경험
### 여행을 실제로 완주할 수 있게
단순 최단거리보다 이동·체류·예약·영업시간·사용자 여유를 같이 본다.
“이동이 너무 많아요”, “예약 시간과 겹쳐요”, “이 장소의 운영시간은 확인이 필요해요”를 일정 옆에 제시한다.
확인하지 못한 영업시간을 열려 있는 것으로 가정하지 않는다. 사용자 순서나 예약을 말없이 바꾸지 않는다.
지각·휴무가 생기면 첫 버전에서 현재 시각 수정·건너뛰기와 남은 일정의 충돌 확인을 제공한다. 자동 대체 코스와 [남은 일정만 다시 정리] 전용 기능은 후속으로 둔다. 이미 방문한 장소와 기록은 보존한다.

### 방문한 사진이 내 지도를 만든다
계획한 장소와 실제 방문한 장소를 다른 상태로 구분한다. 완료한 지점에 본인 사진이 붙는다.
줌이 멀면 지역별 사진 묶음, 가까우면 장소 사진 핀, 누르면 그 여행의 기록이 열린다.
전국을 “정복”하는 압박보다 나의 추억이 쌓이는 느낌을 준다. 실제 방문 지점으로 지도를 채우며 방문하지 않은 지역을 가본 것처럼 칠하지 않는다.
내 기록은 기본 비공개. 공유할 때 사용자가 사진·장소·날짜 공개 범위를 선택한다.

### 여행 친구의 성장은 기록을 위한 보상
표정과 개성을 가진 3D 여행 동행 캐릭터 1종으로 시작한다. 여행 완료로 경험치가 쌓이고 레벨이 오르며 캐릭터의 성장 모습이 드러난다. 초기 3단계 성장은 초보 여행자 → 익숙한 여행자 → 베테랑 여행자처럼 여행 경험을 표현하는 방향으로 제안한다. 배낭·의상·동작 변화는 보조적인 성장 표현이며, 구체적인 외형과 성장 단계는 시안 검토 후 확정한다. 동물형·사람형·상상 속 생명체 중 어느 형태로 할지는 아직 정하지 않는다.
규칙 예시(튜닝 전): 장소 방문 +5, 하루 기록 +10, 여행 마무리 +20. 같은 완료를 취소·재완료해도 순증 경험치는 같고, 사진 추가 업로드만으로 무한 획득할 수 없다.
경험치는 결제·쿠폰과 연결하지 않는다. 출석 강요, 연속 기록 손실, 확률형 보상, 공개 순위 경쟁은 제외한다.
완료는 사용자의 기록 선언이다. 초기부터 GPS 방문 증명을 강제하지 않는다. 경험치 숨기기도 가능하게 한다.

## 7. 여행 상태와 주요 예외
Trip: draft → planned → in_progress → completed / cancelled.
TripStop: planned → visited / skipped. 미방문 장소가 남아 있어도 사용자가 여행을 마무리할 수 있다. skipped는 방문 보상을 주지 않는다.
일정 변경과 여행 기록은 분리한다. 다녀온 사진이 연결된 방문 기록은 계획에서 장소를 빼도 자동 삭제하지 않는다.
숙소 재방문처럼 같은 장소를 서로 다른 날짜/시간에 넣는 것은 허용한다. 장소 중복과 일정 항목 중복은 구분한다.
차량 이동은 주차장→입구 도보가 생긴다. 초기에는 안내하고, 복잡한 혼합 이동 최적화는 후속으로 둔다.
서울 여행에는 대중교통이 중요하다. 첫 버전도 외부 지도에서 대중교통을 선택할 수 있게 하고, 앱 내 최적화 지원은 검증 후 확대한다.
알 수 없는 길을 직선거리로 연결하고 정확한 도보시간인 것처럼 표시하지 않는다.
사진 업로드 실패 시 메모·완료 표시를 유지하고 재시도한다. 위치 권한을 거부해도 지역 입력으로 쓸 수 있다.

## 8. AI와 경로의 역할
사용자 요청 → 조건 추출 → 공식 데이터로 실제 장소 후보 검색 → 식별자·좌표 확인 → AI가 후보 안에서 조합·설명 → 규칙/경로 검증 → 사용자 선택 → 저장.
AI 입력 방식(사용자 결정 2026-09-09): 트리플 ‘맞춤 일정’처럼 지역·날짜/기간·동행·취향·이동수단/일정 밀도를 선택형 단계(칩·버튼)로 받아 추천 초안을 생성하고, 자유 텍스트 입력은 보조로 둔다. 선택값은 구조화된 조건으로 그대로 검색·검증에 쓴다. 결과는 기본 전체 선택 후 개별 해제와 명시적 담기로 확정한다(25절).
LLM은 추천·설명·취향 파악을 맡는다. 좌표·영업시간·평점·예약 가능 여부·정확한 이동시간은 만들어내지 않는다.
사진도 실재 장소의 사용 가능한 사진을 사용한다. 생성형 이미지를 실제 여행지 사진처럼 표시하지 않는다.
경로는 지도/경로 API로 계산한다. 소수 방문지는 제한된 후보 순서를 비교하는 방식으로 시작하고, 예약 시간·출발/도착 고정 조건을 위반하면 해법 없음과 수정 선택지를 제시한다.
“전역 최적 경로”는 보장하지 않는다. UI는 [이동 줄이기]로 표현하고 예상 절약 시간을 비교한다.
자동 재계산은 사용자 입력마다 실행하지 않는다. 버튼 실행, 요청 캐시, 일별 호출 제한, 토큰/비용 기록으로 사용량을 관리한다.

## 10. 화면과 반응형 구조
하단 주요 메뉴 4개: 발견 / 트립플로 / 기록지도 / 여행 친구.
발견: [AI 일정 만들기]를 주 행동으로 두고 선택형 질문으로 진입한다. 자유 텍스트는 보조 입력이며 주변 장소·테마 추천·랜덤 버튼은 그 아래다. 직접 수동 작성 경로도 유지한다.
트립플로: 예정/여행 중/완료 필터와 달력. 여행 상세는 날짜 탭, 지도, 시간순 카드, 고정된 [다음 장소로].
여행 생성·수정에서 시작일과 종료일, 총 N박 N+1일을 표시한다. 여행 상세의 숙소 목록에서 숙소를 등록·수정하고, 날짜별 일정에서 해당 숙소와 체크인·체크아웃 및 숙소 미정 상태를 확인한다.
기록지도: 사용자 사진 중심 지도 + 지역/기간 필터 + 여행별 앨범.
여행 친구: 캐릭터, 경험치, 해제된 장식, 간단한 취향과 개인정보 설정.
장소 상세: 확인된 정보 → 일정에 추가 → 원본 지도 열기 순서. 데이터가 없으면 확인 필요.
PC는 지도와 일정 목록을 나란히, 모바일은 지도 위 하단 시트와 날짜 탭, 태블릿은 두 영역 폭을 조정한다.
드래그만으로 조작하지 않는다. 위/아래 이동 버튼과 키보드 조작을 제공한다. 접근성 목표는 WCAG 2.2 AA에 준한 대비·포커스·입력 라벨·모션 감소 지원이다.

## 11. 3D 방향 제안
전체 길찾기 지도를 3D 게임으로 만들지 않는다. 홈의 작은 디오라마, 캐릭터 성장, 여행 완료 장면에 집중한다.
스타일 제안: 둥글고 말랑한 저폴리/클레이 질감, 작은 배낭을 메고 표정과 개성이 드러나는 여행 동행 캐릭터, 여행한 지역을 떠올리는 작은 오브젝트.
실제 장소 사진은 사진으로, 캐릭터/장식만 제작 이미지 또는 3D 모델로 구분한다.
개발 순서: 정적 3D 렌더 시안 → 캐릭터 1종의 가벼운 실시간 표현 → 필요할 때 장면 확대.
지도 편집 중에는 3D를 멈추거나 언로드한다. 기기 성능이 낮거나 reduced-motion이면 정적 표현을 사용한다.
참고 Notion 링크는 본문/화면을 확인하지 못했다. 본 방향은 사용자 설명에서 도출한 제안이며 해당 참고 화면을 재현한 것이 아니다.

## 12. 기술 방향 초안
반응형 웹/PWA 우선. 초기 후보였던 Next.js 대신 Angular(standalone, signals) + TypeScript를 채택했고 내부 알파 코드는 현재 Angular 20이다. 최신 사용자 지시(2026-09-09)로 Angular 21 업그레이드를 결정했다. 참고 프로젝트와 버전을 맞추고 기능별 구조·NgRx Signals 21.x를 도입하는 설계이며 실제 마이그레이션·검증은 아직 수행하지 않았다(29절·ARCHITECTURE.md). 이 앱은 SSR이 필요 없는 클라이언트 중심 PWA다. 모바일 앱 스토어 배포는 사용성 검증 뒤 결정한다.
DB는 Supabase PostgreSQL로 확정한다. 로그인은 Supabase Auth, 사진은 초기 Supabase Storage 비공개 저장소를 사용하는 방향으로 설계한다. PostGIS는 필요한 공간 질의가 생길 때 적용한다. 무료 플랜으로 시작하되 DB·사진·전송량과 AI·지도 비용을 각각 측정한다. 프로젝트 생성·인증·실제 연동은 아직 완료하지 않았다.
사용자·여행·날짜별 일정·숙소·저장 장소·방문 기록·사진 메타데이터·캐릭터 보상 이력을 저장한다. 사진 파일은 DB와 분리하고, 외부 장소 데이터는 허용된 범위만 저장한다. 사용자 소유권과 RLS로 접근을 제한하며 스키마 변경은 마이그레이션으로 관리한다. 소유자 전용 저장을 먼저 검증한 뒤 27절의 참여자·공유 권한·경비 분담·수령 기록을 추가한다.
사진 압축·용량 제한, 미적용 AI 초안·로그 보관기간, 호출량 제한을 설계해 비용을 관리한다. 구체적인 제한값은 사용량 측정 후 정한다. 무료 한도·비활성 정책은 연동 시 최신 공식 안내로 확인한다. 다른 사진 저장소로의 이전은 필요할 때 검토한다.
지도·장소·경로·AI는 제공자별 어댑터로 분리해 한 곳의 기능/가격 변경이 전체 제품을 묶지 않게 한다.
로그인 전 추천 체험과 임시 여행 바구니를 제공하고, 기기간 동기화·사진 저장 시 가입을 안내하는 흐름을 권한다.
데이터 모델: User, PlaceRef(provider/id), SavedPlace, Trip, TripDay, AccommodationStay, TripStop, Visit, Photo, Companion, XPEvent. 지점과 방문 기록은 분리.
사진은 사용자별 비공개 접근, 파일 크기/종류 검증, 위치 EXIF 처리, 삭제/내보내기를 포함한다. 원본 위치는 업로드 후 기본적으로 제거하고 방문 장소만 별도로 관리한다.
현재 위치는 주변 탐색/다음 길찾기 순간에 사용한다. 상시 이동 궤적 수집은 초기 범위에서 제외한다.
PWA 오프라인은 저장된 일정 텍스트·주소·완료 상태 중심으로 검토하며 상용 지도 타일 오프라인 저장을 약속하지 않는다.
프레임워크는 위와 같이 확정했고, 호스팅·AI 제공자 확정과 유료 계정 개설은 수행하지 않았다. 알파 화면 설계와 구현 상태는 `docs/알파-화면설계-v0.1.md`를 따른다.
[Angular](https://angular.dev) · [PostGIS 지원 문서](https://supabase.com/docs/guides/database/extensions/postgis)

## 13. 출시 단계와 검증
기존 8~10주 예상은 복수 지역·숙소·AI 부분 수정의 상세 설계 이전 가정이다. 일정은 23절의 단계별 통과 기준과 연동 실증 후 다시 산정한다. 기간을 맞추기 위해 기록 보존·사용자 적용 확인·정보 정확성 기준을 생략하지 않는다.

검증 목표(측정 전 목표치):
- 추천에서 장소 3개를 골라 일정 저장까지 처음 사용자 5명 중 4명이 도움 없이 완료.
- 추천 장소는 실제 provider/id 또는 검증된 장소 레코드와 100% 연결. 확인 실패는 추천에서 제외.
- 고정 예약·고정 순서를 자동 정리가 침범하는 회귀 오류 0건.
- iOS Safari/Android Chrome에서 두 지도 앱의 설치/미설치·좌표 순서·도보/차량 조합 확인.
- 완료 취소·재완료·중복 요청으로 경험치 순증이 달라지지 않음.
- 360px 모바일부터 PC까지 핵심 버튼·카드 넘침/키보드 접근 검증.
- API 장애에서도 저장된 여행을 볼 수 있고 사용자 사진·기록이 소실되지 않음.
- 3D를 끈 상태에서 모든 핵심 여행 기능이 동일하게 동작.
- 당일·1박·4박 이상 여행의 날짜 수와 숙박 수가 일치하고, 연박·숙소 변경·숙소 미정 상태에서도 일정을 편집할 수 있음.
- 숙박 날짜 오류·중복·여행 기간 밖 예약과 체크인 시간 충돌을 표시하고, 기간 단축 시 기존 장소·숙소·방문 기록을 자동 삭제하지 않음.
- 실제 운영비는 지도/경로/AI/사진 저장 호출량으로 산출. 초기 운영 목표 상한을 먼저 정하고 실측으로 조정하며 무료 운영을 보장하지 않음.

## 16. 여러 박 여행과 숙소 관리
여행 시작일과 종료일을 지정하면 전체 기간의 날짜별 일정이 생성된다. 당일 여행은 0박 1일로 표시하며, 예를 들어 5월 1~5일 여행은 4박 5일이다. 서비스 이용 기간을 기존 1~3일 제안으로 제한하지 않는다. 장기간 AI 추천은 날짜별로 나누어 생성·수정할 수 있게 한다.

숙소는 방문 장소와 별도로 등록한다. 지도 검색으로 선택하거나 검색되지 않는 숙소·지인 집은 이름과 주소를 직접 입력할 수 있다. 좌표를 확인하지 못한 숙소는 경로 계산 전 위치 확인이 필요함을 표시한다.
필수 정보는 숙소 이름과 체크인·체크아웃 날짜이며, 주소/위치, 시각, 예약 여부, 개인 메모를 함께 관리한다. 정확한 체크인·체크아웃 시각이 없으면 미정으로 표시하고 임의의 시간으로 확정하지 않는다. 예약 여부는 사용자 입력이며 실시간 예약 확인을 뜻하지 않는다.

동일 숙소 연박과 여행 도중 숙소 변경을 모두 지원한다. 예: 4박 5일 여행에서 A 숙소 2박 + B 숙소 2박. 체크아웃 날짜에는 해당 숙소의 숙박을 중복 계산하지 않는다. 체크아웃은 체크인 이후 날짜여야 하며, 여행 기간 밖의 예약이나 숙박 날짜 중복은 확인을 요청한다. 숙소 미정인 날이 있어도 여행 일정을 작성할 수 있다.

날짜별 일정에는 그날 이용하는 숙소와 체크인·체크아웃 정보를 표시한다. 연박 중에는 숙소를 하루 출발·복귀 지점으로 제안하고, 숙소를 옮기는 날에는 이전 숙소 출발 → 방문지 → 새 숙소 도착을 제안한다. 첫날 출발지와 마지막 날 최종 목적지는 별도 설정하며 사용자가 바꾼 출발·종료 지점을 자동으로 덮어쓰지 않는다.
사용자가 확정한 숙소 지점과 체크인·체크아웃 시각은 경로 정리의 제약으로 반영한다. 시간을 맞출 수 없으면 충돌을 알리고 조정안을 제안한다. 짐 맡기기 방문은 별도의 선택 일정 항목으로 추가할 수 있다.

숙소 변경이나 여행 기간 단축 시 영향받는 날짜와 경로를 보여주고 사용자 확인 후 반영한다. 기간 밖으로 밀려나는 장소와 숙소는 재배치 대상으로 보존하며, 방문 기록·사진을 자동 삭제하지 않는다.
숙소 등록은 예약·결제를 대신하지 않는다. 숙소에서 매일 출발·복귀하는 것만으로 방문 경험치를 반복 지급하지 않는다.

## 17. 한 여행에서 여러 지역 이동
하나의 여행에 여러 지역을 등록하고 방문 순서와 날짜별 배치를 편집한다. 하루를 한 지역으로 제한하지 않으며, 지역을 옮기는 날에도 두 지역의 방문지와 숙소를 같은 날짜에 배치할 수 있다. 지역마다 여행을 나누거나 숙소 변경을 강제하지 않는다. 같은 숙소에서 다른 지역을 다녀오는 일정도 허용한다.

3박 4일, 강릉 2박 → 속초 1박의 구성 예시(장소·경로 검증 전):

| 날짜 | 일정 흐름 | 숙박 |
| --- | --- | --- |
| 1일차 | 출발지 → 강릉 방문지 → A 숙소 | 강릉 A 숙소 |
| 2일차 | A 숙소 → 강릉 방문지 → A 숙소 | A 숙소 연박 |
| 3일차 | A 체크아웃 → 강릉 방문지 → 속초 이동 → 속초 방문지 → B 체크인 | 속초 B 숙소 |
| 4일차 | B 체크아웃 → 속초 방문지 → 최종 목적지 | 없음 |

여행 생성·수정에서 복수 지역을 선택하고 여행 상세에서 전체 지역 순서와 날짜별 지역을 표시한다. 지역 간 이동 구간은 날짜별 시간순 일정과 지도에 표시하며, 지역 이름의 중심점이 아니라 앞뒤 실제 방문지·숙소 위치를 기준으로 경로를 조회한다. 이동시간은 하루 총 이동·체류 시간에 포함하고 기존 인접 지점 이동시간과 중복 합산하지 않는다.

AI는 지역별 후보를 날짜별로 나누어 제안하고 지역 간 이동과 확정 체크인·체크아웃, 예약 시각을 고려한다. 시간이 부족하면 방문지 축소·날짜 재배치를 제안하되 사용자 적용 전에는 일정·지역 순서·숙소를 바꾸지 않는다. 조회할 수 없는 이동시간은 확인 필요로 표시한다. 복수 지역의 수동 일정 작성은 초기 범위에 포함하며, 서울 밖 AI 추천 품질은 별도 검증 대상으로 유지한다.

초기 경로 비교는 기존 하루별 차량/도보 범위를 유지한다. 기차·시외버스 등 미지원 이동은 사용자가 이동수단과 출발·도착 시각을 직접 기록하고 외부에서 확인할 수 있게 한다. 입력값은 사용자 입력으로 표시하며 실시간 시간표·예약 확인이나 혼합 이동 자동 최적화를 보장하지 않는다. 이동정보가 미정이면 시간 충돌 판단도 확인 필요로 남긴다.

지역 순서나 이동일을 바꿀 때 영향받는 방문지·숙소·예약과 이동 구간을 보여주고 확인 후 반영한다. 지역 목록에서 제거한 지역의 일정이나 방문 기록·사진을 자동 삭제하지 않는다. 검증에는 위 3박 4일 예시, 하루 두 지역, 다른 지역 당일 왕복, 이동시간 누락·중복 합산 방지, 숙소 도착 시간 충돌, 지역 순서 변경 시 데이터 보존을 포함한다.

## 18. AI로 숙소 등록 초안 만들기
여행 상세의 AI 입력 또는 숙소 목록의 [AI로 추가]에서 자연어로 숙소 등록을 요청한다. 예: “이번 여행 첫 2박은 강릉 A호텔, 마지막 1박은 속초 B호텔로 숙소 추가해줘.” AI는 현재 선택한 여행의 기간과 지역을 바탕으로 숙소 후보, 체크인·체크아웃 날짜, 숙박 수, 날짜별 연결 내용을 초안으로 보여준다. 예시의 호텔 이름은 설명용이며 실제 숙소 검색 결과를 뜻하지 않는다.

흐름: 자연어 요청 → 조건 해석·실제 숙소 검색 → 초안 검토·수정 → [일정에 적용] → 숙소 등록 및 날짜별 연결. 여러 숙소를 한 번에 요청할 수 있고, 적용 전에 숙소와 날짜를 각각 수정하거나 후보를 제외할 수 있다. 초안 생성·수정만으로 확정 일정이나 기존 숙소를 변경하지 않는다.

여행이 10월 1~4일인 경우 “첫 2박”은 10월 1일 체크인·3일 체크아웃, “마지막 1박”은 3일 체크인·4일 체크아웃으로 풀어 보여준다. 여행 날짜가 없거나 “마지막 날 숙박”처럼 귀가일 이후 숙박인지 불명확하면 날짜를 확인한다. 동명 숙소가 여러 곳이면 주소·지역을 보여주고 선택을 요청한다. 검색 실패 시 숙소를 지어내지 않고 재검색 또는 직접 입력을 제공하며, 직접 입력값과 위치 미확인 상태를 구분한다.

“속초에서 마지막 1박 묵을 숙소 추천해줘”처럼 숙소 미정 요청은 실제 검색으로 확인한 후보와 추천 이유를 먼저 보여준다. 사용자가 숙소를 선택한 뒤 등록 초안으로 전환한다. 실시간 가격·객실 재고·예약 가능 여부를 추측하지 않고, 체크인·체크아웃 시각과 예약 여부도 확인된 정보나 사용자 입력이 없으면 미정으로 둔다. 제공자가 안내한 기본 이용 시각과 사용자가 확정한 도착 시각은 구분한다. 서울 밖 AI 숙소 추천 품질도 별도 검증 대상이다.

적용 전에는 숙박 날짜 오류·중복·여행 기간 초과, 기존 숙소와 경로 제약에 미치는 영향을 확인한다. 기존 숙소 교체는 변경 전후를 보여주고 사용자가 명시적으로 선택한 경우에만 반영한다. 초안 검토 중 여행 기간이나 기존 숙소가 바뀌면 최신 일정으로 재검증하고 변경된 초안을 다시 확인받는다. 같은 적용 요청의 재시도로 숙소가 중복 등록되지 않아야 한다.

AI 실패 시에도 검색·직접 등록은 계속 사용할 수 있다. 숙소와 예약 메모는 기본 비공개이며, AI 등록은 실제 예약·결제를 수행하지 않는다. 검증에는 여러 숙소 일괄 초안, 상대 날짜 해석, 동명 숙소 선택, 미확인 정보, 적용 전 일정 불변, 기존 숙소 충돌, 오래된 초안 재검증, 중복 적용 방지를 포함한다.

## 19. 처음부터 끝까지의 기본 사용 흐름
기본 대상은 본인과 친구들이며 한 사람이 자신의 국내 여행 일정을 관리한다. 여러 명이 함께 가더라도 동시 편집은 후속 범위다. 짧은 여행으로 사용성을 검증하되 여행 기간이나 지역 수를 그 길이로 제한하지 않는다. 일반 공개와 월 운영비 상한은 미정이다.

| 단계 | 입력과 동작 | 결과 및 미정 처리 |
| --- | --- | --- |
| 여행 만들기 | 자연어 또는 직접 입력으로 날짜·복수 지역 설정 | 이름은 수정 가능한 임시 제목. 날짜가 없으면 날짜 미정 초안으로 저장 |
| 조건 보완 | 출발지·최종 목적지, 일자별 차량/도보, 하루 시작·종료 시각 | 필요한 계산 시점에만 질문. 동행·취향은 선택이며 없는 정보를 확정하지 않음 |
| 골라 담기 | 실제 검색 후보 또는 직접 장소 선택 | 날짜가 없거나 배치 전이면 미배치 목록에 보관 |
| 숙소 넣기 | 검색·직접 입력·AI 초안으로 숙박 등록 | 체크인·체크아웃 날짜 확인. 숙소 미정인 밤도 허용 |
| 날짜별 배치 | 방문지·식사·휴식·숙소·이동을 정리 | 전체 보기에서 날짜와 지역을 오가며 수정 |
| 여행 준비 | [준비 완료]로 저장 상태 변경 | 누락·충돌을 요약하되 정보 확인 완료나 예약 완료로 해석하지 않음 |
| 여행 중 | 사용자가 [여행 시작], 다음 장소 안내·완료·건너뛰기 | 현재 날짜 일정 중심. 다른 날짜와 전체 보기도 계속 접근 가능 |
| 여행 마무리 | 사용자가 [여행 완료], 사진·메모 기록 | 미방문을 방문으로 바꾸지 않고 여행별 기록과 성장 결과 표시 |

날짜 미정 초안에는 달력 날짜의 숙박이나 일별 영업 가능 여부를 확정하지 않는다. 날짜 설정 후 숙박 날짜를 확인하고 미배치 장소를 배치한다. 종료일이 시작일보다 빠르면 수정을 요청한다. 날짜·이동수단·위치가 빠진 구간의 정확한 도착시간은 제시하지 않는다.
로그인 전에는 같은 기기에서 초안을 저장하는 흐름을 설계하며 저장 실패·비영구 보관 가능성을 표시한다. 계정 저장 시 기존 초안을 미리 보여주고 한 번만 가져온다. 동기화·사진 저장은 로그인 후 제공한다. 저장 중·저장됨·저장 실패를 구분하고 실패한 입력은 재시도할 수 있게 유지한다.

## 20. AI 변경은 공통 초안 규칙으로 통일
AI는 현재 선택된 여행과 사용자가 지정한 날짜·항목에 한해 변경안을 만든다. “3일차 카페 하나 빼고 숙소에 일찍 도착하게 바꿔줘”는 3일차를 대상으로 하며, 다른 날짜로 옮겨야 하면 별도 변경으로 드러낸다. 대상 날짜나 장소가 모호하면 확인한다.

1. 현재 일정에서 변경 범위와 유지할 조건을 표시한다.
2. 추가·제외·순서·시간·숙소 변경과 이유를 초안으로 제시한다.
3. 변경 전후 일정, 조회 가능한 이동시간, 예약·숙소 충돌, 미확인 정보를 비교한다.
4. 사용자가 변경 묶음을 선택하고 [일정에 적용]한다. 서로 의존하는 변경은 하나로 묶고 부분 선택 시 다시 검증한다.
5. 적용 직후 [되돌리기]를 제공한다. 이후 편집이 있으면 복원 영향을 먼저 보여주고 최신 데이터와 충돌하는 복원을 조용히 수행하지 않는다.

예약 시각, 사용자 고정 순서·출발/종료점, 확정 숙소, 실제 방문·건너뛰기 기록은 기본 보존한다. 고정 조건 변경이 필요한 요청은 어떤 조건을 해제하는지 별도 확인받는다. 방문 기록과 사진은 일정 복원 대상에서 제외한다. 숙소 초안도 같은 규칙을 사용한다.
초안 생성 중 수동 편집이 있으면 최신 일정으로 재검증해 다시 확인받는다. 실패·취소·시간 초과 시 기존 일정은 유지한다. 동일 적용 요청 재시도는 한 번만 저장한다. 적용은 하나의 변경 묶음 전체가 성공하거나 기존 상태를 유지해야 한다.

## 21. 하루 시간과 여행 전체 확인
하루 일정은 방문지 외에도 장소 미정 식사·휴식·짐 보관과 사용자가 설정한 여유시간을 포함한다. 식사·휴식의 제안 시간은 수정 가능한 계획값으로 표시하고 사용자 확인 없이 확정 예약처럼 다루지 않는다. 장소 미정 활동은 시간을 차지하지만 위치가 정해지기 전까지 관련 이동시간은 확인 필요다.
하루 소요시간은 이동 + 활동 체류 + 별도 여유시간으로 계산한다. 식당 체류를 식사 블록과, 지역 간 이동을 일반 이동과 중복 계산하지 않는다. 자유시간과 고정 예약 시각을 구분하며 체크인 가능 시간 범위·체크아웃 마감과 사용자가 정한 도착 시각도 구분한다. 숙박 자체를 다음 날 관광 활동 시간에 합산하지 않는다.
필수 정보가 누락된 구간 이후 도착시각은 미확인으로 두거나, 사용자 입력 추정값을 쓴 경우 그 가정을 표시한다. 알려진 값만으로 충돌이 확인되면 충돌을 표시할 수 있지만 누락 때문에 확인할 수 없는 일정을 가능하다고 단정하지 않는다.

여행 상세의 기본 보기는 [전체 / 날짜별 / 숙소]다. 전체 보기는 각 날짜를 ‘날짜·지역 → 주요 일정 → 숙소’ 한 줄 요약으로 보여주고, 지역 간 이동, 알려진 총 이동시간, 미확인 구간 수, 숙소 미정, 예약 충돌을 함께 표시한다. 날짜를 누르면 해당 날짜 편집으로 연결된다. 아직 배치하지 않은 장소는 별도 목록에 유지한다.
충돌은 해당 항목에서 수정할 수 있어야 한다. 확인된 시간 충돌, 위치·영업정보 확인 필요, 사용자가 남겨둔 숙소 미정은 구분한다. 모든 밤에 숙소를 강제하지 않으며 필요하면 ‘숙박 계획 없음’을 직접 표시한다. 빈 날짜나 미정 숙박 때문에 초안 저장을 막지 않는다. 모바일에서도 전체 보기와 날짜 전환이 지도 조작에 가려지지 않도록 설계한다.

## 22. 여행 중 변경과 기록 보존
여행 중 첫 화면은 오늘 일정, 다음 목적지, 다음 예약·숙소 시각이다. 자동 위치 추적 없이 사용자가 현재 시각·출발 지점 수정과 완료·건너뛰기를 실행한다. 늦게 출발하면 조회 가능한 경로로 남은 도착 예상과 충돌을 다시 확인한다. 조회 실패 시 마지막 조회 시점과 갱신 실패를 표시한다.
건너뛰기는 실제 방문과 분리하며 사용자가 다시 계획 상태로 돌릴 수 있다. 다른 장소를 자동으로 끼워 넣거나 다음 날 숙소를 바꾸지 않는다. 수동 순서 수정과 20절의 명시적 AI 부분 수정은 가능하지만, 휴무·날씨 감지에 따른 자동 대체와 전체 잔여 일정 자동 재계획은 후속 단계다.
오프라인에서는 이미 기기에 저장된 일정 텍스트·주소를 보여주고 최신 조회가 아님을 표시한다. 완료·메모 입력은 동기화 대기 상태로 보관하며 서버에 저장된 것처럼 표시하지 않는다. 재접속 시 중복 적용을 방지하고 다른 기기의 변경과 충돌하면 사용자에게 비교를 제공한다. 사진 업로드 실패가 완료 상태와 메모를 지우지 않아야 한다. 상용 지도 타일의 오프라인 제공은 이 범위에 포함하지 않는다.
여행 종료는 사용자가 결정하며 예정 날짜가 지났다는 이유만으로 자동 완료하지 않는다. 사진·기록·숙소 메모는 기본 비공개이고 공유 기능 도입 전 외부 공개는 수행하지 않는다.

## 23. 실행 순서와 검증 기준
아래는 권장 진행 순서다. 기획 문서의 완료가 화면·앱 구현이나 실제 여행 검증의 완료를 뜻하지 않는다.
초기에는 데이터 관계·소유권을 설계한 뒤 샘플·임시 저장으로 여행 생성 → 장소·숙소 등록 → 전체 보기 → 재열기를 구현한다. 최신 우선순위는 이 흐름 이후 실제 지도·장소·경로 연결 → 선택형 AI 실제 연동과 화면 검증 → Supabase 로그인·서버 저장·RLS 연결이다(26절). Supabase 프로젝트는 아직 없으며 지도·AI 화면 작업의 선행조건이 아니다. 친구들이 실제 데이터를 넣기 전 서버 저장·권한을 검증한다. 화면 코드와 저장 접근은 분리하며 임시 저장에 복잡한 동기화를 구현하지 않는다.

| 단계 | 산출 범위 | 다음 단계 통과 기준 |
| --- | --- | --- |
| A. 사용 흐름 설계 | 여행 생성, 전체·날짜별·숙소 보기, AI 변경 비교, 여행 중 화면의 입력·상태·오류 명세 | 날짜 미정부터 3박 4일 두 지역·두 숙소까지 문서 시나리오에 막힌 흐름이 없음 |
| B. 내부 알파 | 수동 검색·일정·복수 지역·숙소·식사/휴식, 전체 보기, 저장·복구, 지도앱 연결 | 처음 사용자 5명 중 4명이 도움 없이 여행과 두 숙소 등록·날짜 수정·다음 장소 열기 완료 |
| C. AI 검증 | 확인된 후보 선택, 숙소 초안, 지정 범위 수정, 비교·적용·되돌리기 | 고정 조건 침범·미확인 정보 확정·중복 적용·방문 기록 손실 0건. 오래된 초안과 실패 시 기존 일정 보존 |
| D. 외부 베타 | 동행·선택형 공유·경비 정산(27절), 여행 중 지연·건너뛰기, 동기화 복구, 비공개 사진 지도, 정적 대체 가능한 3단계 캐릭터, 기본 주변·랜덤 탐색 | 공유 권한·비공개 필드 차단·정산 잔액 검증, 지도앱 설치/미설치·접근성·사진 권한·오프라인 복구 확인과 소규모 실제 여행 검증 |
| E. 후속 확장 | 자동 대체 코스, 공동 편집, 엽서·개인화, 고도화한 3D·홍보 영상 | 핵심 흐름 사용성과 운영비를 측정한 뒤 개별 우선순위 결정 |

5절의 첫 사용 가능한 버전은 외부 베타까지의 목표이며 내부 알파가 모든 기능을 포함하는 것은 아니다. 베타의 캐릭터 성장은 정적 표현으로도 검증할 수 있고 실시간 3D를 출시 필수조건으로 삼지 않는다. Higgsfield 등 제작 도구는 캐릭터·영상 시안이 필요한 시점에 검토하며 핵심 기능 의존성이나 결제 확정 항목이 아니다.
대표 검증 묶음: 날짜 미정 → 날짜 확정, 당일 여행, 3박 4일 두 지역·두 숙소, 4박 이상, 숙소 미정·당일 왕복, AI 부분 적용·되돌리기, 고정 예약 충돌, 이동정보 누락, 늦은 출발·건너뛰기, 오프라인 기록·재접속 충돌. 강릉·속초 예시는 흐름 검증이며 해당 지역 추천·경로 품질 실증을 대신하지 않는다.
다음 작업은 A단계 화면별 설계다. 이름·캐릭터 외형은 임시 표기로 진행할 수 있다. Supabase 계정 연결은 개발 단계에서 진행하며, 유료 사용·일반 공개 배포는 운영비 상한과 공개 범위를 정한 뒤 별도로 진행한다.

## 24. 여행 가계부와 숙소 예약 정보 (사용자 요청 2026-09-09, 후속 범위)
트리플의 여행 가계부처럼 여행별로 예산과 지출을 기록하고 일정과 연결한다. 알파 다음 단계에서 설계·구현하며 실제 결제·은행 연동은 하지 않는다.

- 예산: 여행 단위 총예산(선택)과 카테고리별 예산(선택). 예산이 없어도 지출 기록은 가능하다.
- 지출 항목: 금액(원), 카테고리(숙소·교통·식비·관광·쇼핑·기타), 날짜(여행 일자 또는 날짜 미지정), 연결 대상(장소 일정 항목 또는 숙박, 선택), 결제 수단(선택), 메모, 사진(후속). 통화는 원화만 우선한다.
- 보기: 여행 총액, 날짜별 합계, 카테고리별 합계, 예산 대비 잔액. 날짜별 일정 화면의 항목 카드에서 해당 지출을 바로 추가·확인한다.
- 숙소 연동(트리플 참고): 숙소 등록·편집에 숙박 요금, 예약 번호, 예약처(예: 앱 이름·링크)를 선택 입력하고, 요금을 입력하면 ‘숙소’ 카테고리 지출로 함께 기록할지 확인한다. 예약 확인서 연동·실시간 요금 조회는 하지 않는다.
- 동행 정산: 결제자·부담 대상별 계산과 수동 수령 기록으로 확장한다(27절). 실제 송금·은행 확인은 외부에서 수행한다.
- 원칙: 지출 기록은 기본 비공개다. 장소·숙박을 일정에서 제외·삭제해도 지출 기록은 자동 삭제하지 않고 ‘연결 해제’로 보존한다. 저장 실패 시 입력을 보존하고 재시도한다.
- 검증 시나리오: 예산 없이 지출만 기록, 숙박 요금 입력 시 지출 자동 제안·거부, 날짜 미지정 지출, 카테고리·날짜별 합계, 항목 삭제 후 지출 보존, 기간 단축 시 기간 밖 날짜 지출 보존.

## 25. 트리플 참고 흐름·디자인과 선택형 담기 (2026-09-09 사용자 결정)
참고 분석과 화면별 적용 기준: `docs/트리플-맞춤일정-분석.md`. 공개 웹의 시작 → 5단계 조건 입력 → 추천 결과 → 날짜 탭을 직접 확인했다. 네이티브 앱 내부와 저장 이후 편집은 미검증이다. 이 절은 후속 AI 화면 기획이며 기존 Angular 수동 알파의 구현 완료 항목과 구분한다.

- 입력: 지역 → 날짜/기간 → 동행 → 취향 → 이동수단/일정 밀도. 큰 질문·선택 카드·진행 상태·하단 고정 다음 버튼의 구성을 참고하고 뒤로가도 입력을 보존한다. 자유 텍스트는 보조다. 복수 지역·날짜 미정·긴 여행을 계속 지원한다.
- 결과 구성: 지역·기간·조건 요약 → 지도 → 날짜 탭 → 순번과 사진이 있는 장소 카드 → 하단 고정 담기. PC는 지도·목록을 나란히 배치한다. 카드는 이름·분류·지역·추천 이유를 중심으로 읽고 상세 정보는 펼쳐 본다.
- 사용자 핵심 차이: 추천 결과의 검증된 방문 항목은 모든 날짜에서 처음에 전체 선택한다. 원치 않는 항목을 해제한 뒤 [선택한 장소 N개 일정에 담기]를 눌러 저장한다. 처음 선택되어 있다는 이유로 자동 저장하지 않는다.
- 선택 조작: 전체/날짜별 선택·해제와 부분 선택 표시, 장소별 체크박스, 총 선택 수, 0개 선택 시 담기 비활성화. 상세 열기와 선택 동작을 구분하며 날짜 이동에도 선택을 보존한다. 별도 대안 후보·미검증 장소·기존 확정 숙소는 자동 선택 범위가 아니다.
- 선택 변경: 해제한 항목은 다시 선택할 수 있도록 목록에 남긴다. 관련 경로는 재확인 필요로 표시하고 알려진 합계만 갱신한다. 선택 클릭마다 유료 경로 조회하지 않으며 [이동 다시 확인] 또는 담기 전 검증으로 갱신한다. 미확인 시간은 사실로 표시하지 않는다.
- 적용: 모든 날짜의 선택 항목만 추가하고 기존 숙소·고정 예약을 보존한다. 같은 장소의 다른 날짜 방문은 항목별 선택을 유지한다. 실패 시 초안·체크 상태 보존, 재시도 중복 방지, 오래된 결과 재검증, 적용 후 되돌리기는 20절과 일치시킨다. 재추천·교체 시 해제 상태를 몰래 초기화하지 않는다.
- 디자인: 트리플과 유사한 위계·여백·둥근 카드·날짜 탭·번호 마커·고정 버튼 구조를 따른다. 2026-09-09 전체 리뉴얼에서 사용자가 세 후보(인스탁스 앨범·스티커 플래너·클린 앱 표준) 중 ‘클린 앱 표준’을 선택했다: 미지근한 회백색 바탕, 흰 카드와 1px 구분선 목록, 밑줄 탭, Noto Sans KR 한 가족의 굵기 위계, 코랄 강조 하나(트리플 파랑·민트 제외), 표시용 귀여운 서체·스티커 장식 없음. 지도 로딩·빈 화면·오류 상태도 같은 체계로 디자인한다. 참고 이미지·브랜드 자산은 분석용이고 우리 제품 자산으로 복제하지 않는다. 표준 체크박스와 충분한 대비·포커스를 적용한다.
- 확인 기준: 입력 5단계 왕복, 처음 전체 선택, 일부/전체 해제, 날짜 간 선택 보존, 0개 선택, 같은 장소 재방문, 경로 미확인, 담기 실패·중복 재시도, 기존 숙소 보존, 360px·PC·키보드 접근. UI 샘플과 실제 AI·지도 연동 검증을 구분한다.

## 26. 지도·AI 실제 연결을 우선하는 개발 지시
사용자 최신 방향: Claude Code가 기존 Angular 앱을 수정하면서 지도와 실제 추천 데이터를 먼저 연결해 화면을 검증한다. 실행 순서는 지도 표시·장소 검색 → 날짜별 번호 마커·목록 연결 → 실제 경로 조회 → 선택형 AI 추천과 선택 담기 → Supabase 연결이다. 화면 정적 배치 작업은 API 없이도 진행 가능하며, 미연결 부분 때문에 독립적인 UI 작업까지 중단하지 않는다.
지도 표시, 장소 검색, 도보/차량 경로 계산, AI 생성은 별개 기능이다. 기존 후보를 기준으로 현재 공식 지원 범위·표시 결합 조건·무료 한도·키 요구사항을 확인하고 제공자를 정한다. MCP 설치만으로 앱 사용자용 API가 연결되지는 않는다. 공급자 선택·유료 사용이 필요한 경우 비용과 적용 범위를 먼저 명시한다.
지도에는 검증된 좌표의 장소·숙소를 표시하고 날짜 탭·카드 선택·번호 마커를 동기화한다. 미확인 좌표는 가상 위치로 대체하지 않는다. 실제 경로가 없을 때 방문 순서 안내선을 쓴다면 안내선임을 표시하고 경로·정확한 소요시간으로 표현하지 않는다. 선택 해제 후 경로 갱신 규칙은 25절을 따른다.
AI는 검증된 장소 후보와 사용자 조건·숙소 제약을 바탕으로 날짜별 초안을 구성한다. 결과는 처음 전체 선택하고 사용자가 해제한 뒤 선택 항목만 저장한다. 최소 한 번의 실제 생성→선택 해제→담기 흐름을 검증하되 실패·이용량 제한 시 입력과 기존 일정을 보존한다.
Angular 화면과 별도로 개발용 서버 엔드포인트를 두어 AI 및 비공개 검색/경로 API를 호출한다. AI·서버 비밀키는 로컬 환경변수로 관리하고 `.env.example`에는 이름과 설명만 기록한다. 브라우저 공개용 지도 키는 공급자 지침에 따라 사용 도메인을 제한한다. 요청 크기·호출 횟수 제한을 적용하고 인증 없는 개발 서버를 일반 공개하지 않는다. 로그인 기반 사용량 제한은 Supabase 연결 후 실제 친구 사용 전에 검증한다.
2026-09-09 제공자 결정(지도 표시·장소 검색): 카카오맵 JavaScript SDK + services 라이브러리(키워드 검색·주소 변환)를 1순위로 쓴다. 근거: JavaScript 키 하나로 지도·검색을 브라우저에서 처리하고 등록 도메인으로 제한할 수 있으며, 개발자 계정의 첫 활성화 앱에 무료 쿼터(지도 Web SDK 일 300,000건, 키워드 검색 일 100,000건)가 결제 수단 없이 제공된다. 네이버 클라우드 Maps는 대표 계정 1개에 무료 이용량이 있으나 NCP 계정 절차와 초과 과금 구조가 있어 2순위, 네이버 개발자센터 지역 검색(일 25,000건)은 브라우저 직접 호출이 막혀 서버 프록시가 필요하므로 후속 보조 후보다. 경로(도보·차량)는 별도 연동이며 카카오 길찾기 REST·TMAP을 실증 후 정한다.
AI 실행 결정(2026-09-09 사용자): AI 추천은 외부 유료 API 대신 로컬 LLM으로 실행한다. 로컬 개발용 서버 엔드포인트가 로컬 모델을 호출하며 비용·키 관리는 서버 쪽에 둔다. 모델·성능 검증은 tasks 6.5에서 한다.
2026-09-10 연결 준비: 사용자 제공 RTX 3090 24GB·RAM 64GB·Windows 11 사양에 대해 Ollama + qwen3.5:9b를 첫 실행 후보, 27b를 품질 비교 후보로 권장한다. 모델 확정·설치·실연결 완료를 뜻하지 않는다. 설정 방법과 PC 간 연결, 샘플과 실제 생성의 검증 구분은 [LOCAL-LLM.md](LOCAL-LLM.md)를 따른다. 로컬 생성에는 유료 AI API 키가 필요 없으며 전기료와 지도/서버 비용은 별도다.
이번 문서는 코드 수정 지시이며 연동 완료가 아니다. 지도·검색은 카카오로 확정했고 실제 키 연결 여부는 HARNESS.md의 검증 기록을 따른다. AI 제공자는 로컬 LLM으로 방향을 정했으며 실제 연결은 미완료다. 계정·키가 필요하면 안전한 로컬 입력을 안내하고, 샘플 화면·통합 테스트·실제 API 검사 결과를 각각 보고한다.

## 27. 친구와 여행 공유·정산 (추가 기획, 2026-09-09)
공유와 정산을 친구 사용 단계의 기능으로 추가한다. 구현 순서는 기존 지도 → AI → Supabase 연결 이후 동행·공유 권한 → 가계부·정산이다. 화면 초안과 계산 검증은 먼저 가능하지만 실제 공유는 서버 저장·인증·권한 검증 후 제공한다. 아래는 비용과 구현량을 줄이기 위한 기본 설계이며 실시간 공동 일정 편집·자동 송금은 후속 검토다.

### 공유 흐름과 공개 범위
- 여행 상단 [공유] → [일정 링크 만들기] 또는 [동행 초대]. 링크를 만든 뒤 사용자가 복사해 전달한다.
- 일정 링크: 날짜·장소 항목을 처음에는 전체 선택하고 해제할 수 있다. 숙소 이름·위치는 기본 제외하고 별도로 선택한다. 공개 미리보기 후 읽기 전용 스냅샷을 발행하며 원본 수정은 자동 공개하지 않는다. [공유 내용 갱신]에서 다시 검토한다.
- 링크는 로그인 없이 소지자가 볼 수 있음을 발행 전에 안내한다. 기본 만료 7일, 즉시 해제·재발급을 지원한다. 서버는 매 요청에 만료·해제를 검사하고 공유 응답을 공개 캐시에 보관하지 않는다. 이미 복사·캡처한 내용까지 회수할 수 있다고 표현하지 않는다.
- 사진·개인 메모·예약번호·예약 확인서·개인 지출·정산 내역은 일정 링크에서 제외한다. 필드 허용 목록으로 별도 공유 데이터를 만들며 원본 여행 전체를 내려준 뒤 화면에서 숨기는 방식은 사용하지 않는다.
- 동행 초대: [초대 코드]와 일회용 초대 링크를 함께 제공한다(기본 7일). 친구는 [트립플로 → 코드로 참여]에서 코드를 입력하고 로그인 후 참여를 요청한다. 비로그인 입력은 로그인 뒤 이어가되 코드·로그인만으로 권한을 부여하지 않고 소유자가 승인해야 참여가 완료된다. 소유자는 참여 승인·제거·초대 해제를 관리한다. 참여자는 선택된 여행 일정과 공동 경비·정산만 조회하며 일정 수정은 소유자가 담당한다. 숙소 이름·위치 공유는 별도 동의하고 비공개 필드는 계속 제외한다.
- 초대 코드는 혼동하기 쉬운 문자를 제외한 영문 대문자·숫자 8자리 난수로 생성하고 `ABCD-EFGH` 형태로 표시한다(형식 예시, 실제 유효 코드 아님). 하이픈·공백·대소문자는 정규화한다. 코드 하나로 여러 친구가 만료·해제 전 요청할 수 있고 일회용 링크와 사용 규칙을 구분한다. 여행별 활성 코드는 하나이며 재발급하면 이전 코드는 즉시 무효다. 생성 결과는 복사할 수 있고 다시 표시할 수 없는 경우 재발급으로 안내한다.
- 코드는 서버에서 검증하고 원문 대신 서버 비밀값을 사용한 HMAC을 저장한다. 계정별·접속 출처별 시도 횟수를 제한하고 과도한 요청은 잠시 차단한다. 유효하지 않음·만료·해제는 같은 안내로 처리하며 승인 전 여행 제목·날짜·숙소·경비를 노출하지 않는다. 코드 원문을 분석 로그에 남기지 않는다.
- 참여 요청은 여행·계정별 하나로 유지한다. 중복 클릭은 같은 대기 상태를 반환하고 이미 참여한 계정은 기존 여행으로 이동한다. 거절된 요청의 반복 제출은 새 코드 또는 소유자 재초대로 제한한다. 만료·해제된 초대의 승인 전 요청은 만료 처리해 재요청하게 한다. 이미 승인된 멤버는 코드 만료·재발급으로 제거하지 않으며 멤버 제거로 별도 관리한다. 제거된 계정도 재참여 시 다시 승인을 받아야 한다.
- 동행의 일정 조회는 최신 서버 저장본을 기준으로 한다. 멤버 제거는 이후 서버 접근을 차단하지만 기존 지출·정산의 사람 식별자와 기록을 삭제하지 않는다. 공동 일정 편집은 이번 1차 범위에 포함하지 않는다.

### 경비와 정산 흐름
- 여행 [경비·정산] → 동행 등록 → 지출 추가 → 정산 보기 → 실제 송금 후 수령 기록. 처음에는 여행 소유자가 장부를 관리하고 승인된 동행은 공동 내역을 조회한다. 미가입 친구는 이름으로 등록하고 이후 계정 연결 시 소유자가 확인한다. 이름 중복을 허용하되 내부 사람 ID로 구분한다.
- 지출은 기본 개인 기록이며 [공동 경비]를 명시적으로 선택해야 동행에게 공개하고 정산에 포함한다. 개인 기록·합계는 작성자만 조회한다. 공동 지출은 결제자 1명, 부담할 사람 1명 이상, 금액, 날짜·분류·메모를 기록한다. 나누어 결제한 경우 결제자별 항목으로 등록한다.
- 기본 분배는 선택한 사람끼리 균등 분배이며, 항목별 불참자를 제외하거나 사람별 부담액을 직접 입력할 수 있다. 3박 4일 중 2박만 참여한 친구도 숙박·식사별 대상을 선택한다. 참여 기간만으로 기존 지출을 자동 재분배하지 않는다.
- 원화 정수만 사용한다. 지출은 양수, 직접 부담액은 0 이상이며 합계가 지출 금액과 같아야 저장한다. 균등 분배의 나머지 1원은 해당 항목에 저장한 참여자 순서대로 배정해 반복 계산 결과를 고정한다. 새 동행 추가·탈퇴가 과거 분담 내역을 바꾸지 않는다.
- 사람별 결제 합계와 부담 합계를 계산해 ‘누가 누구에게 얼마를 보내면 되는지’를 제안한다. 순잔액 = 결제 합계 − 부담 합계 + 보낸 수령확인 금액 − 받은 수령확인 금액. 양수는 받을 돈, 음수는 보낼 돈이며 모든 사람의 합은 0원이어야 한다. 송금 제안은 원 지출·부담 내역을 함께 확인할 수 있게 하고 최소 송금 횟수를 보장하지 않는다.
- 예: A가 숙소 180,000원(ABC 균등), B가 식사 60,000원(AB만)을 결제하면 A는 90,000원 받을 돈, B는 30,000원 보낼 돈, C는 60,000원 보낼 돈이다. 제안은 B→A 30,000원, C→A 60,000원이다.
- 실제 송금 후 소유자가 보낸 사람·받은 사람·금액·날짜를 입력하고 [수령 기록]한다. 일부 수령을 지원하며 금액이 양쪽 현재 미정산 잔액을 넘으면 저장을 막는다. ‘수동 기록’ 표시와 수정 이력을 남기고 은행에서 확인된 송금처럼 표현하지 않는다. 오입력은 원 기록을 취소 처리하고 이유를 남겨 잔액을 복원한다.
- 지출 수정·삭제 후에도 기존 수령 기록을 보존하고 차액을 다시 계산한다. 기존 수령 때문에 반대 방향 잔액이 생기면 반환 필요 금액으로 표시한다. 정산금은 여행 지출 총액에 다시 더하지 않는다. 모든 잔액이 0일 때 현재 내역 기준 정산 완료로 표시하고 새 지출이 생기면 다시 미정산으로 바뀐다.

### 데이터·권한·검증
- 기존 여행·지출에 TripParticipant(회계상 사람), TripMember(계정 권한), TripInvite(링크/코드·만료·해제), TripJoinRequest(계정별 참여 요청·승인), TripShare(만료·해제·공개 스냅샷), ExpenseShare(항목별 부담액), SettlementTransfer(수동 수령·취소 이력)를 추가 설계한다. 회계상 사람과 접근 권한을 분리하고 이름이 같다는 이유로 미가입 회계 참여자에 계정을 자동 연결하지 않는다.
- 소유권 RLS를 유지하면서 승인된 멤버의 허용된 읽기만 추가한다. 원본 숙소·개인 기록 테이블을 멤버에게 통째로 공개하지 않는다. 공개 링크는 검증된 토큰으로 허용된 스냅샷만 읽는다. 정산 저장은 장부 버전 확인·원자적 처리·중복 요청 방지로 재시도와 동시 변경에 대응한다.
- 초기에는 Supabase 기반 저장과 일반 링크 복사로 구성한다. 공유·정산 계산에 AI나 별도 유료 메시지·결제 API를 필요로 하지 않는다. 실시간 구독 없이 진입·수동 새로고침·저장 후 갱신하고 최신 갱신 시각을 표시한다. 서버 연결 실패 시 입력을 보존하되 저장 완료로 표시하지 않는다.
- 검증: 만료·해제·추측한 링크, 초대 재사용·미승인·제거된 계정, 타 여행 ID 직접 요청, 비공개 필드 응답 누출, 공유 스냅샷과 원본 분리, 1원 나머지·불참자·중복 이름·직접 분배 합계 오류, 예시 ABC 계산, 일부 수령·중복 재시도·취소·정산 후 지출 수정·새 지출·동시 변경·총 잔액 0원, 360px·키보드 흐름을 확인한다.

## 28. 여행 상단 요약과 동행 프로필 (2026-09-09 사용자 요청)
요청 요소는 D-day, 몇 박 며칠, 장소 구분, 지출, 동행 프로필이다. 참고 `AA.png`는 아직 전달 경로를 확인하지 못했으므로 정확한 배치·그라데이션·‘장소 구분’의 시각 표현은 이미지 확인 후 결정한다. 아래는 확인 가능한 텍스트 요구사항이며 화면 구현 완료가 아니다.

- 여행 제목과 구분된 기간·지역·지출 정보를 표시한다. 기간은 날짜 범위와 N박 N+1일, 당일은 0박 1일이다. 날짜 미정은 미정으로 표시하며 D-day를 만들지 않는다.
- 국내 여행의 Asia/Seoul 달력 날짜 기준으로 시작 전 `D-N`, 시작일 `D-day`, 이후 종료 예정일까지 `여행 중 · N일차`를 표시한다. 종료 예정일 경과는 `일정 날짜 지남`으로 표시하고 사용자 명시적 여행 완료와 구분한다. 날짜 경계·앱 재진입 시 갱신한다.
- 장소 구분은 우선 기존 지역 순서(예: 강릉 → 속초)를 별도 영역으로 표현한다. 장소 수를 표시할 경우 일정 장소와 숙소·활동을 혼합 집계하지 않는다. 지역별 세부 탭 여부는 AA.png 확인 후 정한다.
- 지출은 실제 저장된 경비에서 집계하며 개인/공동 범위를 이름으로 명시한다. 동행에게는 허용된 공동 경비만 표시한다. 미연결·조회 실패는 금액 대신 준비 중/불러오지 못함으로 표시하고, 조회 성공 후 기록이 없을 때만 0원을 사용한다. 정산금은 지출 합계에 다시 더하지 않는다.
- 동행 프로필 영역과 [+ 초대] 진입 위치는 초대 서버 기능보다 먼저 화면에 준비할 수 있다. 미연결 상태는 기본 사람 아이콘과 `동행 초대 준비 중` 안내를 쓰며 가상의 이름·사진·참여 인원은 넣지 않는다. 디자인 검토용 샘플 프로필은 샘플임을 표시한 환경에서만 제공한다.
- 연결 후에는 승인된 멤버의 허용된 이름·프로필만 표시하고 사진이 없으면 이니셜/기본 아이콘을 쓴다. 참여 완료 인원과 승인 대기 인원을 섞지 않는다. 대기 요청의 프로필은 소유자만 승인 목록에서 조회하고 요청자는 자신의 대기 상태만 확인한다. 공개 일정 링크에는 동행 프로필을 자동 포함하지 않는다. [+ 초대]에서 코드 생성·복사·재발급과 링크 초대로 이어진다.

## 29. 아키텍처·상태관리와 Angular 21 업그레이드 (2026-09-09)

착수 시점은 현재 진행 중인 작업이 끝난 뒤 사용자가 별도 리팩터링을 지시할 때다. 지금 기능 작업을 중단하거나 코드·의존성을 변경하지 않는다. 후속 작업 시작 시 최신 구현을 기준으로 설계와 실제 차이를 확인한다.

- 최신 결정은 Angular 21 + NgRx Signals 21.x + 기능별 구조다. 참고 프로젝트의 MD뿐 아니라 실제 서비스 코드를 확인했고, 서비스 내부 private `signalState`와 읽기 전용 공개 상태를 기본으로 삼는다. 현재 설치·구현은 Angular 20이며 업그레이드 완료가 아니다.
- 상세 원본은 [ARCHITECTURE.md](../ARCHITECTURE.md)다. 비교한 대안, 채택·조정 이유, 원본 프로젝트 파일과 공식 문서 링크, 상태 수명과 구현 순서를 함께 기록했다.
- 현재 app/를 유지하면서 여행·AI·경비·동행·장소 기능 안에서 feature/ui/data/model/util을 구분한다. 작은 UI는 기본 signal, 날짜·필터는 URL, 여러 하위 화면의 편집 상태는 해당 기능 서비스, 로그인은 전역 세션에서 관리한다.
- 저장 실패 입력은 여행·사용자별 세션 보관소로 분리한다. 늦은 조회와 이전 저장 성공이 최신 입력을 덮어쓰지 않으며, 저장 중 추가 편집을 저장 완료로 표시하지 않는다. 새로고침 후 미저장 복구는 지속 저장 설계 전에는 보장하지 않는다.
- Angular 21 공식 마이그레이션을 먼저 검증하고 상태 서비스 정리·Zoneless를 각각 검증한다. 기본 폼은 typed Reactive Forms, 조회는 Promise/HttpClient·RxJS다. 21에서 experimental인 Signal Forms·rxResource는 필요 시 독립된 흐름에서 실증한다.
- 기반 업그레이드 뒤 지도→AI→Supabase→동행·공유→정산 순서를 유지한다. Supabase 연결 시 기존 전체 여행 CRUD 외에 버전·중복 방지·트랜잭션을 갖춘 용도별 명령을 설계한다. OpenSpec tasks 9절은 미완료 구현 작업이다.
